# E04 档案字段保存竞态

以 Linux Electron 44.9.1、独立 Xvfb 和 Playwright Electron 的临时 Vault 运行。基线是 `9f870c0` 的构建，修复版使用当前工作树中的 E04 改动重新构建。两个批次都保留 Playwright 单 worker，通过两路 `yes >/dev/null` 增加 CPU 竞争，宿主同时有其他活动。后台进程在本批退出时清理。

| 批次 | 执行次数 | 通过 | 失败 | 失败率 |
| --- | ---: | ---: | ---: | ---: |
| 基线 | 20 | 16 | 4 | 20% |
| 修复直接切换入口后 | 20 | 20 | 0 | 0% |
| 最终候选构建 | 20 | 20 | 0 | 0% |

三批都运行 `xvfb-run -a pnpm e2e tests/e2e/workflows/archives-tabs.spec.ts -g 'E04 同一' --repeat-each=20`。原始日志和失败 trace 见 [runs.md](runs.md)。基线失败是第 5、10、11、14 次，均为 5 秒内未出现 `999`。失败时磁盘仍有 `电话: "123"` 并包含 Markdown 新正文。三批均未观察到 Electron 启动失败。该样本量只能描述本次观察的失败率。

Markdown 和档案标签切换会卸载当前内容组件。此前档案表单可以在旧 Markdown 会话销毁或写盘完成前载入旧版本。字段写入带着那份版本号，后续 flush 无法改变已捕获的参数。先完成 Markdown 写入时字段请求被拒绝。另一路顺序可让字段抢先写入，导致旧 Markdown 会话基于旧版本的保存冲突。

`archives-tabs.spec.ts` 的「E04 在途 Markdown 保存完成后」以 Playwright 路由暂停真实 `notes.save`。修复前的首次探针刻意让档案字段抢先提交，`999` 落盘而 Markdown 正文没有落盘。最终的回归用例先打开档案表单并留下档案标签，再切到 Markdown 并暂停保存。此时点击已有档案标签，界面须等待保存回执。解除暂停后加载档案、改字段，再关闭两种标签并由档案记录重新打开 Markdown 核对两项编辑。

直接切换和点击已有档案标签共用同一保存入口，先排空编辑器并保存，再重新读取档案查询。档案视图等待登记表的会话引用就绪后再显示表单，版本校验仍由底层文件服务执行。文件标签或 Vault 已变化时，旧保存回执不会跳转界面。
