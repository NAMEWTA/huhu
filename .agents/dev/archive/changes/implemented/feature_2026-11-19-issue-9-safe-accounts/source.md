## 正文

## 目标

将保险箱（`plugins/safe`）重构为**个人网站 / APP 账号密码管理器**：一个网站或 APP 是一个条目，条目下可以保存多个独立账号，每个账号都有账号、密码、手机号、邮箱和备注；条目共用名称、网址及多个彩色标签。

同时取消 Safe 作为 SSH、Git 同步、Agent CLI、自动化和邮件的共享凭据服务。连接哪个服务，就在对应模块的设置或新增流程中维护其认证信息。**SSH 新增主机时直接配置用户名、密码或私钥，工具使用已保存的主机 ID 即可连接，不需要先创建保险箱条目。**

这是面向个人工作台的产品重构。保留已有插件框架、统一 Dispatcher、Vault 和成熟加密能力，避免增加企业权限模型、通用凭据代理或另一套运行时。

## 1. 需求来源、现状与关联工作

依据 2026-11-17（UTC+8）用户明确补充：

1. Safe 只管理网站 / APP 的个人账号密码，不承担外部 token、SSH 等机器认证信息的供给。
2. 一个条目必须支持多个账号，每个账号独立填写五个字段。
3. 名称、网址属于条目公共信息；标签也关联条目，支持多个标签和不同颜色。
4. SSH 按 Motty 的使用方式自管认证信息，UI、MCP、CLI 操作同一份主机配置。
5. 同步修正现有 open Issues，整体保持适合个人工作台的复杂度。

**源码基线：** [Huhu `main@913264045cee1818497a37a57715c664aa85a1ae`](https://github.com/NAMEWTA/huhu/commit/913264045cee1818497a37a57715c664aa85a1ae)。本 Issue 基于源码及现有需求的静态核对；以下行为、接口和验收均为待实现目标，不能当作当前已经完成。

### 1.1 当前实现与目标的差异

| 当前事实 | 本次调整 |
| --- | --- |
| Safe 每项只有一组 `account + value`，并带 `password / ssh-key / token / env` 类型及 `allowedModules` | 改为网站 / APP 条目、多个账号、彩色标签；删除对个人密码管理无用的机器凭据类型和模块授权字段 |
| `safe.items.*` 按单个秘密读写，`secretUse.resolve` 向其他插件提供解密值 | 用条目 / 账号 / 标签能力表达新业务；取消共享解密服务和 `safe://` 认证引用协议 |
| 目前只有 `value` 加密；账号等元数据保存在明文 JSON | 新账号的五个字段整体加密；条目名称、网址、标签也属于个人数据，按第 5 节保护 |
| SSH、Git 同步、shell `envRefs` 存在对 Safe 的实际依赖 | 所有消费者与 Safe 一次调整，不能只改保险箱页面 |
| Git 同步会收集部分 `.huhu` 模块数据；Vault 备份也会收集模块目录 | 重新区分可同步配置、密文、本机密钥与临时运行资料，防止自管凭据后意外入库或随备份泄露 |

源码入口见第 10 节。Safe 当前的主密码、加密、手动锁定、自动锁定、修改主密码可作为复用基础；不能因重构重新发明密码学实现。

## 2. 用户看到的产品模型

### 2.1 条目、账号与标签

| 层级 | 字段 | 规则 |
| --- | --- | --- |
| 条目 `SafeEntry` | `id`、名称 `name`、网址 `url`、`tagIds`、`accounts`、创建 / 更新时间 | 一个网站或 APP 一个条目；名称必填，网址可空；公共信息只维护一次 |
| 账号 `SafeAccount` | `id`、账号 `account`、密码 `password`、手机号 `phone`、邮箱 `email`、备注 `notes`、创建 / 更新时间 | 同一条目下可有任意多个账号，各自独立编辑、删除、显示或复制 |
| 标签 `SafeTag` | `id`、名称 `name`、颜色 `color` | Safe 内统一维护，一个标签可关联多个条目，一个条目可关联多个标签 |

稳定 ID 用于定位，名称或账号内容不能充当主键。不同网站出现相同账号，或同一条目存在同名账号，都不能自动合并或覆盖。

**表单默认规则：** 新建条目至少包含一个账号；账号字段必填，手机号、邮箱、备注可空，密码允许暂空但明确显示“未设置”。账号字段是自由文本，不强制是邮箱；手机号按字符串保存，保留 `+` 和前导零。邮箱和网址在非空时做基本校验，不发起账号验证或登录请求。这里的可空规则是为减少个人录入负担作出的实现建议，五个字段均必须存在并可编辑。

密码只存储用户输入的原值，不能自动 trim、格式化或因编辑其他字段而清空。账号的手机号、邮箱、备注也不能因为当前视图没有展开而在保存时丢失。

### 2.2 示例

“Google”条目：

- 公共名称：Google；公共网址：`https://accounts.google.com`。
- 标签：“个人”（蓝色）、“工作”（橙色）。
- 账号 A：个人登录账号、独立密码、个人手机号、恢复邮箱、备注“主账号”。
- 账号 B：工作登录账号、另一组密码、工作手机号、工作邮箱、备注“用于项目协作”。

编辑账号 B 的密码不能覆盖账号 A；调整 Google 的网址只修改公共信息。标签可以随时增删，不要求每个账号重复填写网站信息。

**网站密码记录与实际服务登录互不联动。** 即使 Safe 保存了 Gmail 账号，Mail 的 OAuth 授权仍在 Mail 中完成；Safe 不自动填充、同步或更新 Mail / SSH / Git 的认证配置。用户主动复制密码属于个人操作，不构成插件间凭据服务。

## 3. 页面与完整操作流程

### 3.1 主页面

沿用现有 Safe 模块贡献和 Huhu 设计系统：

- 顶部提供搜索、新建条目和锁定入口。
- 列表展示条目名称、网址摘要、账号数量和标签，不直接展示密码或备注全文。
- 提供“全部”“无标签”以及标签筛选，标签管理入口可直接创建、改名、选色和删除标签。
- 选中条目后展示公共信息与多个账号卡片 / 行；每个账号清晰区分五个字段，提供编辑、删除、复制账号、复制密码及显隐操作。
- 页面适配窄窗口、长中文名称、长网址、多个标签和大量账号。复用现有表单、菜单、对话框、列表与主题 token，不引入第二套 UI 框架。

密码默认遮罩；展开详情或切换账号不自动显示密码。只有明确的显示 / 复制操作才请求相应明文，不能一次把所有条目的所有密码预取进列表缓存。复制成功与失败有反馈；不把密码写入 toast、调试日志或错误文本。

### 3.2 新增、编辑与删除

1. **新建条目：** 填公共名称 / 网址 → 选择或新建标签 → 添加一个或多个账号 → 一次保存。保存失败保留当前表单，不出现半个成功条目。
2. **添加账号：** 在现有条目内新增账号，不要求重复填条目名称和网址。
3. **编辑账号：** 定位 `entryId + accountId`；只更新对应账号。密码“保持原值”“设置新值”“明确清空”语义区分，遮罩占位符不能被当成新密码保存。
4. **删除账号：** 明确提示删除对象。删除最后一个账号时提示改为删除整个条目，或取消；不默默产生空条目。
5. **删除条目：** 明确包含的账号数量，删除整个条目及其账号；不会删除标签定义或其他条目。
6. **取消 / 关闭编辑：** 有未保存修改时提供继续编辑或放弃；自动锁定或离开 Vault 时清除含明文的界面状态，明确提示未保存内容不会被写入未加密草稿。

使用现有原子写和并发冲突处理，避免两个页面 / MCP 调用同时编辑时悄悄覆盖对方。这里不引入多人协作、分布式锁或复杂事务平台。

### 3.3 标签与检索

- 标签颜色使用 Huhu 现有语义色 / 调色板，保存稳定颜色标识；明暗主题下可读，不能只靠颜色区分。
- 同名标签在 Safe 内复用，避免重复创建；改名或换色后所有关联条目同步显示。
- 删除标签只解除标签关联，不删除条目或账号。
- 同时选择多个标签时沿用项目已有的“包含全部已选标签”筛选语义，并明确显示规则；搜索词与标签条件共同生效。“无标签”与具体标签互斥选择。
- 解锁后搜索条目名称、网址、标签名称及账号 / 手机号 / 邮箱 / 备注；不搜索密码。账号字段命中时定位到所属条目和对应账号。
- 检索仅在 Safe 解锁后的受控内存数据中进行，不将账号明文导入全局全文索引、通用日志或可同步的搜索缓存。
- 锁定后清除列表详情、搜索结果、已显示密码与相关查询缓存；不得从旧缓存绕过锁定。

## 4. 模块边界：认证资料由使用它的模块维护

### 4.1 统一的归属规则

| 使用场景 | 配置入口与所有者 | 实际使用方式 |
| --- | --- | --- |
| 网站 / APP 的个人密码记录 | Safe 条目与账号页面 | 用户查看 / 复制；经授权也可由 Safe 自身能力进行管理 |
| SSH 密码、私钥、口令、代理认证等 | SSH 新增 / 编辑主机和相应设置 | SSH 读取自身配置并交给认证实现；系统 SSH agent / 身份文件仍按已有或 Motty 目标语义使用 |
| Git HTTPS 的用户名 / token | Versioning 的 Git 同步设置 | Versioning 自管，仍以短生命周期方式传给 Git；SSH remote 沿用实际系统 SSH / agent 路径 |
| 原生 Agent CLI 登录 | 对应 CLI 原生登录机制 | Huhu 启动 CLI，不替各 CLI 建立第二套登录账号系统 |
| Agent CLI 自定义启动环境 | Agent CLI 对应配置 | Agent CLI 解析自己的配置，运行时传给子进程 |
| 自动化脚本专用环境 | Automations 脚本 / 规则配置 | Automations 解析自己的配置，通过既有 Agent CLI 执行合同传递 |
| 邮箱密码、OAuth token、邮件 AI Key | Mail 账号 / 邮件设置 | Mail 自己保存、刷新、更新和清理 |

“自管”表示领域所有权和使用流程归本模块，**不表示明文保存在普通 JSON、Git 或任务日志中**。可以复用无业务含义的加密 / 本机存储函数；不能再包一层通用 `secretUse` 服务，换名字后让所有模块继续依赖一个中心保险箱。

Safe 主密码只保护 Safe 的个人账号资料。Safe 未初始化、锁定、停用或修改主密码，不应影响已正确配置的 SSH、Git 同步、Agent CLI、自动化或 Mail。

### 4.2 SSH 的直接使用流程

桌面与 MCP / CLI 共用同一 SSH 业务 handler：

1. 新建主机时填写主机、端口、用户名，并选择密码 / 私钥 / agent 等认证方式。
2. 需要保存的秘密在此流程中写入 SSH 自有的受保护存储；用户不需先去 Safe 建条目，也不需填写 `safe://`。
3. 保存返回主机 ID 和脱敏结果；列出 / 查看配置默认返回认证方式及“已配置 / 未配置”等状态。
4. `ssh.connect(hostId)` 或后续对应能力读取该主机的自身认证配置，完成主机密钥校验、认证和连接。
5. 未信任主机、缺少凭据、私钥口令错误、交互认证待答等返回可处理状态；按 #7 的查询 / 回答 / 取消合同继续，不以打开 Safe 页面作为恢复步骤。

保持 #7 的 Motty 复刻范围，包括跳板、代理、OTP、SFTP、转发和交互认证；本 Issue 只修正认证资料的归属，不缩减这些目标。模块内部如需凭据 ID，它仅是 SSH 自有数据定位，不是用户必须操作的跨模块秘密 URI。

### 4.3 Git/versioning 必须同步去耦

本项由本 Issue 直接完成：

- Git 同步设置移除 Safe 凭据下拉选择和对 `safe.items.list` 的依赖，改为本模块填写 / 更新 HTTPS 用户名和 token / 密码；凭据属于实际配置的 remote，不能无条件发给新的主机。
- 移除 `secretUse` 解析与 `safe.unlocked` 恢复逻辑。认证缺失、无效或本机受保护存储不可用时显示 Git 同步自身的状态；更新凭据或用户重试后恢复。
- 保留当前系统 Git、Git SSH remote 和既有网络认证执行边界；不借此捆绑 Git 二进制或引入新的 Git 引擎。
- 秘密不写入带用户信息的 remote URL、`.git/config`、命令行参数或可同步配置。沿用现有 ASKPASS 的受限传递与临时文件清理思路，检查错误 / 取消路径。
- Git SSH remote 与 Huhu 的 SSH 插件是不同调用链；本次不凭空建立它们之间的新凭据依赖。

### 4.4 Agent CLI / Automations 必须同步去耦

- 删除现有 shell `envRefs → safe:// → secretUse.resolve` 路径，以及所有对应类型、UI、fixture、manifest 声明和文档。
- 按上表归属保存启动环境；非秘密环境与需要保护的环境值区分。不要把旧 `envRefs` 简单改成明文 `env` 后写进可同步 JSON。
- 自动化需要的秘密由 Automations 解析并按既有内部执行合同传给 Agent CLI；仅传到目标子进程所需环境，不写入任务正文、评论、结果或通用调度事件。
- UI / MCP / CLI 创建与更新这些配置时使用同一模块 handler；避免“桌面能填写，外部工具仍要走 Safe”的两条实现。
- 对 herdr/Core 的运行恢复环境、临时文件、会话输出和清理路径做针对性验证；不能因 Huhu 自己的会话 JSON 没有明文，就声称子进程恢复文件也不会保留秘密。不承诺 JavaScript 字符串能够可靠物理零化。
- 保持 #4 / #5 的统一执行、取消、恢复与身份语义；不增加第二套自动化执行器。

## 5. 存储、加密、锁定与备份

### 5.1 Safe 自身

- 复用当前主密码派生、随机数据密钥、AES-GCM、密码修改与锁定基础；变更封装时保留认证加密、唯一 nonce 和正确 AAD 绑定，不自行设计加密算法。
- **整个账号载荷加密**，包含账号、密码、手机号、邮箱、备注；条目的名称、网址、tagIds 及标签目录的名称 / 颜色同样加密，不以明文复制到全局索引或普通业务配置。
- 建议沿用每条目一个受保护载荷、账号嵌套数组的简单结构，标签在 Safe 内统一维护。存储层只暴露恢复与定位必要的最小元信息；不为这些数据新建服务、数据库或通用实体平台。
- 条目和账号 ID 稳定；原子保存成功后才刷新 UI。标签改名 / 删除后的关联必须正确，文件损坏不能被当作空库自动覆盖。
- 保留设置 / 解锁 / 锁定 / 自动锁定 / 离开锁定 / 修改主密码的可用路径。锁定后敏感状态和内存索引释放；在途请求不能在锁定后把明文重新写回界面缓存。
- 如保留现有审计页，调整为简洁“操作记录”：记录动作、实体 ID、时间、结果，去掉模块取密授权的产品表达；不记录密码、手机号、邮箱、备注或完整表单。不要扩展为企业审计平台。

### 5.2 其他模块的本机秘密存储

当前基线没有可直接复用的通用 OS keychain 实现，不能在计划中写成“现成接入即可”。

实施 S0 必须先检查 Huhu 已有代码、Motty / one-mail / ORCA 的实际实现及成熟平台能力，确定**一套最小的本机受保护保存方式**，写清以稳定 Vault 身份 + 所属插件 + 实体 ID 隔离的命名空间、密钥落点、Engine 访问路径和不可用时的用户提示，防止不同 Vault 的同名主机 / 邮箱误读凭据。可复用基础函数或成熟库；不建立跨插件秘密目录、模块 ACL / allowlist、凭据分发网关或新的主密码产品。

最低行为约束：

- 各模块拥有自己的凭据生命周期；保存、更新、删除随所属主机 / 账号 / 配置操作，不受 Safe 生命周期控制。
- 普通配置只保留必要的非秘密信息或本模块内部定位；秘密不明文落到可 Git 同步文件。
- 若采用系统安全存储或本机密钥，密钥不可与密文一同放入可同步 / 可导出的 Vault；不可用时给出明确错误，不静默降级为明文。
- MCP / CLI 经已运行的 Huhu Engine 使用同一模块配置；默认调用返回脱敏结果，运行操作直接使用已有配置，不要求先 reveal。
- 跨设备恢复可采用“恢复非秘密配置后重新输入 / 授权”的简单策略并明确提示，不要求为个人工作台新增跨设备密钥托管平台。

这项小范围技术选择应通过实际平台与调用路径验证后锁定；不能为追求“通用”反向把 Safe 再做成所有模块的必选基础设施。

### 5.3 Git 同步与 Vault 备份

必须分别处理，不能把“加密”“不在列表中展示”和“不会被导出”视为同一件事：

- 当前 Git 同步规则包含 `safe/`、`ssh/hosts/`、`automations/scripts.json` 等范围。调整后确保其只含允许同步的配置 / 密文，不夹带新保存的秘密或本机解密密钥。
- 当前 Vault 数据包默认收集大部分 `.huhu` 目录，不能只改 Git ignore 就认为备份已经安全。
- Safe 的可恢复备份应包含条目、账号、标签和必要 keyring 的完整密文材料；恢复仍需要原主密码。不能只备份 sealed 而漏掉解密所需 keyring，也不能宣称支持找回遗忘的主密码。
- SSH / Git / Agent CLI / Automations / Mail 的本机认证资料按各自既定保存方式明确排除或保留不可独立解密的密文；跨机不能使用时明确要求重新配置。账号 / 主机定义与秘密能否恢复要分别显示。
- 保留现有 Vault 导出 / 恢复基础；不默认新增明文 CSV 密码导出、云同步或跨设备凭据服务。

## 6. 统一能力与外部工具

保险箱不再给其他插件供应登录秘密，**不等于把 Safe 自身的正常管理能力永久禁止给用户的工具使用**。继续遵守 #6 的“用户按功能选择开放”。

建议业务能力分组（具体命名按现有规范锁定，不保留旧 / 新两套公开接口）：

| 分组 | 业务操作 | 默认输出 / 约束 |
| --- | --- | --- |
| `safe.entries.*` | 列表、详情、新建、修改公共信息、删除 | 列表为摘要；详情不默认回传密码 |
| `safe.accounts.*` | 添加、修改、删除、显式查看秘密 | 普通读写结果脱敏；查看密码是单独可授权的敏感读取 |
| `safe.tags.*` | 列表、新建、改名、换色、删除 | 关联条目行为与 UI 一致 |
| Safe 生命周期 / 设置 | 状态、初始化、解锁、锁定、修改主密码、自动锁定设置 | 保持明确的锁定错误、失败反馈和用户选择开放机制 |

统一要求：

- UI、MCP、CLI 共用 schema、handler、锁定检查和权限分发，不由 UI 直接写文件。
- 写入敏感字段的能力可以接收用户提供的值，但响应、审计和错误不能回显；CLI 不要求把密码放在易进入 shell history 的位置参数，使用既有受控输入方式。
- 普通账号详情可在解锁和相应权限下展示账号 / 手机号 / 邮箱 / 备注；这些仍是个人数据。密码通过显式敏感读取获得，主密码不提供读取接口。
- 只有用户明确开启对应功能时，外部工具才可读取或修改；新增能力默认策略与 #6 一致。允许用户授权显式查看，不用永久 `exposable:false` 偷换用户需求。
- 内部认证代码不得通过调用 `safe.accounts.reveal` 绕回共享凭据模式；跨模块认证引用、订阅 Safe 解锁恢复连接等路径都要删除。
- 若模块自己的凭据查看需要对外开放，遵守 #6 的独立敏感能力及用户选择，不通过 Safe 代查。
- 更新能力说明、Agent Guide、CLI 帮助和 MCP schema，移除旧“先建 Safe 凭据再连 SSH”的教程。

## 7. 旧路径清理与现有数据处置

延续相关 Issues 的无兼容方向：最终只保留新模型和新调用方式，不保留旧版 Safe UI、`secretUse` 兼容壳、`safe://` 解析器、模块授权字段、旧 / 新双写或长期迁移框架。

**无兼容不代表可以删除真实密码。**

实施前盘点旧保险箱数据及消费者引用，给出一次性可审查处置：

- 旧个人密码项可以显式转换为“一个条目 + 一个账号”，缺失的网址 / 手机号 / 邮箱 / 备注留空；必须保全原账号与密码。

- 更新正式契约、manifest 依赖、示例 Vault、测试、用户文档和现行项目说明；归档文档保留历史身份，不当作新规范继续执行。
