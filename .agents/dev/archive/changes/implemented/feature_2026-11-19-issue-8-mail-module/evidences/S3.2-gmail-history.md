# S3.2 Gmail history 与重连

[任务票据](../tasks/S3.2-gmail-history.md)。下文记录当时的验证范围与结果。

## 请求范围和存储

- 已授权的 Gmail OAuth 账号使用已有受保护凭据及 `https://mail.google.com/` scope。Engine 只向 Google 的 `gmail.googleapis.com/gmail/v1/users/me` 发起 Gmail API 读取。该项目需启用 Gmail API。测试由进程内已信任的 issuer 装配指定本地地址，账号和调用者无 API 地址配置项。 [Gmail API 授权范围](https://developers.google.com/workspace/gmail/api/auth/scopes) · [Gmail 消息列表](https://developers.google.com/workspace/gmail/api/guides/list-messages)
- 首扫从 `profile` 核对授权地址并在列表前取得 history 锚点。只列已选 `INBOX`，排除垃圾、废纸篓和草稿，最多 8 页，每页 25 个 ID。正文每组最多 5 个并发 GET，单封原文限 2 MiB，每轮抓取约 18 MiB 原文字节，缓存每条路径最多 200 封和 24 MiB Base64 原文字符。初始锚点使扫描期间到达的变化可在下一轮对账。 [Gmail 同步指引](https://developers.google.com/workspace/gmail/api/guides/sync) · [Gmail 消息资源](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages)
- history 只请求必要字段，读取整轮分页后才处理 MIME 和提交游标。Inbox 外事件不会下载正文。已缓存正文只复核 `id` 及标签，未见过且范围待确认的候选也先复核标签。删除、归档及移动到垃圾或废纸篓会撤出受影响的 Inbox 正文与定位。请求中断、限流或暂时不可用保留当前缓存、游标和未确认通知。history 已失效，或超过 20 页、400 个候选变化或一轮正文预算时，受限重扫当前 Inbox 并显示原因。 [Gmail history 分页](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list) · [Gmail 正文读取](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get)
- 缓存在既有可重建的 `.huhu/cache/mail` 范围。新记录将有效传输、本机原文、待交付通知与两个互相独立的游标放入同一次条件写。Gmail `historyId` 与 `nativeId` 保持字符串，客户端用当前 Vault 的账号、目录和不透明本地消息 ID 打开。Gmail 原生 ID 用作下载和定位，并与账号绑定及提供商独立计算本地 ID。授权不足或 API 未启用时回退到实际 IMAP，同一账号非 Inbox 的已选目录继续使用 IMAP。
- Gmail 标读仅提交本地覆盖，返回 `remoteSynced: false`，后续同步不会把该覆盖重新变成未读。回复沿用本机同账号原信、SMTP 授权和发件队列。首扫、补扫及路径切换静默，新未读 Inbox 消息在增量提交后通知。丢失通知确认时重交同一 ID。归档及删除的定位会失效，联系人阅读仍不输出 Bcc。

已核对 one-mail 固定提交 `d1be24d5bb83c2da7123b167f119d5abd169b0af` 的 `src-tauri/src/mail/sync/gmail_api.rs` 和 `src-tauri/src/mail/sync/mod.rs`。复用了按 Inbox 初始化、history 过期重扫和 IMAP 回退的流程，接入 Huhu 自有缓存与通知。Gmail 原生 ID 和分页游标贯穿同一 Huhu 本机路径。

## Windows 复验

在隔离 Windows Vault 上用 `plugins/mail/test/oauth-engine.test.ts` 启动真实 Engine dispatcher。授权经本地签名 issuer 验证 PKCE 后保存至 `ModuleCredentials`。Gmail fixture 验证实际 bearer 和 GET，邮件读取、回复和通知经现有能力。SMTP 的 DATA 只发到本机夹具。

| 操作 | 实际结果 |
| --- | --- |
| 错误 profile 地址 | 一次 profile 请求，零 IMAP 和正文请求，刷新拒绝 |
| 205 封初始 Inbox | 8 个列表请求、200 次 RAW，搜索能读到窗口内最早一封。两个相同数字开头的原生 ID 读到各自正文，初扫通知为零 |
| history 第二页返回 503 | 请求 2 页，正文请求为零，原缓存与游标保留。重开 Vault 后仍从原字符串游标及第一页开始 |
| 两页成功重试 | 4 次 minimal、1 次 RAW。删除、归档各撤出一个定位，保留事先提交的标读。已知垃圾零请求，范围外候选仅 minimal。通知存储收到一条，丢确认及重启后重交同一个 ID，定位指向新邮件的 Gmail 原生 ID |
| 沿新增邮件回复 | 同账号投递到本机 SMTP，收件人为原发件人，线程头为该信 RFC Message-ID，Bcc 未参与收件或联系人搜索 |
| 游标 404、长 history | 404 后以 profile 重建，仅抓实际 Inbox 的 3 封。另以 20 页持续存在 nextPageToken 模拟过长历史，回到相同有界窗口。两种重扫都无新增通知 |
| Gmail API 403 后恢复 | 实际切换到独立 IMAP 缓存，旧 Gmail 定位不可打开。重启后 API 恢复，只请求一次保留的 Gmail 游标，无首扫或重复通知 |
