# S3.1／S4.1 Google 与 Microsoft 邮箱授权

## 交付行为

- Google 使用桌面授权码流程、回环 `127.0.0.1` 回调、PKCE S256 和离线权限。`https://mail.google.com/` 是 Gmail 的 IMAP 和 SMTP OAuth scope。用户关闭发送时，Huhu 保存收件专用配置。 [Google 桌面 OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) · [Google OIDC 配置](https://accounts.google.com/.well-known/openid-configuration) · [Gmail XOAUTH2](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol)
- Microsoft 使用 `common` 公共客户端、回环 `localhost` 回调、PKCE S256 和 `offline_access`。默认请求 Exchange IMAP 权限，开启发送时才请求 Exchange SMTP 权限。个人 Outlook 在验证 ID token 的租户后使用 `smtp-mail.outlook.com`，组织账号使用 `smtp.office365.com`。两者均使用 `outlook.office365.com` 的 SSL/TLS IMAP，SMTP 使用 587 和 STARTTLS。 [Microsoft 授权码流程](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow) · [回调注册](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url) · [Exchange OAuth](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth) · [Microsoft ID token 声明](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference) · [Outlook.com 邮箱设置](https://support.microsoft.com/en-au/outlook/pop-imap-and-smtp-settings-for-outlook-com) · [Exchange Online SMTP](https://learn.microsoft.com/en-us/exchange/mail-flow-best-practices/how-to-set-up-a-multifunction-device-or-application-to-send-email-using-microsoft-365-or-office-365/)
- Engine 依据已配置提供商的 token endpoint 返回的 scope 识别 Exchange 授权。IMAP 协议认证及目录发现成功后才提交账号。`Mail.ReadBasic` 显示仅有 Graph 基本权限，Graph token 无法用于默认邮箱路径。Graph 额外 consent 仍待确认。 [Microsoft Graph 权限说明](https://learn.microsoft.com/graph/permissions-reference)
- 每个授权会话归属当前 Vault Engine、发起者、提供商及目标账号。新授权预分配账号 ID 和选择发现出的 INBOX，重新授权以现有账号 ID、修订和已选目录提交。回调验证 host、路径、单次 state、签名 ID token 的发行方、受众、时效及 nonce。提供商身份与用户填写地址相符后再做 IMAP 探测。取消、超时及 Vault 卸载收束回调和交换，账号更新经过条件写入。浏览器回调页请用户返回 Huhu 核对结果。 [Microsoft OIDC 配置](https://login.microsoftonline.com/common/v2.0/.well-known/openid-configuration)
- access token 和 refresh token 以同一凭据包存入既有 `ModuleCredentials`，并绑定账号修订及 OAuth 主体。每个账号共用在途刷新，轮换后的凭据先经条件提交再给协议客户端。无效授权使账号进入重新授权状态。Workbench 只收到当前 Engine 的主机提示、会话状态、脱敏原因及已保存的账号 ID、可用协议和发送状态。授权 URL 通过受信任的宿主函数打开。

参考了 `one-mail` 固定提交 `d1be24d5bb83c2da7123b167f119d5abd169b0af` 的 `src-tauri/src/oauth/mod.rs` 授权码、PKCE 与提供商 scope。传输继续用项目已安装的 ImapFlow、Nodemailer 和 Huhu 凭据事务。

## Windows 验收

`plugins/mail/test/oauth-engine.test.ts` 在隔离的 Windows 临时 Vault 上启动真实 Engine 和能力分发器。仅测试装配注入回环发行方、受信浏览器打开函数和合成时间。发行方验证真正提交的 PKCE verifier，返回签名 ID token。IMAP 与 SMTP 使用 TCP 回环夹具并检查实际 XOAUTH2。测试邮件的 DATA 只进入夹具。

| 操作 | 观察结果 |
| --- | --- |
| 查未配置状态、从默认 CLI 调用或由另一个 Web 身份读取会话 | 未配置客户端在能力和 UI 模型上不可用。默认 CLI 调用被拒绝，其他 Web 身份无法读取已有会话 |
| 发错 state、提交有效回调、重放 | 错误 state 触发零次交换。有效请求通过 S256 并完成一次交换。回调重复无法新增邮箱 |
| Google 和 Microsoft 相同地址授权、分别发送到夹具 | 两条路径均经真正的 IMAP XOAUTH2 和 SMTP XOAUTH2。在 Microsoft 仅授 IMAP 时保存为收件专用，Exchange/个人 Outlook 端点有单独断言 |
| Microsoft 返回 Graph 基本权限、Graph 其他权限、缺失权限，或协议拒绝 | 分别观察 `graph-metadata-only`、`wrong-resource`、`permission-missing` 或 `protocol-unavailable`，授权不提交账号 |
| 回调拒绝、等待超时、取消后迟到、关闭 Vault 时交换未完成 | 状态分别为拒绝、过期或取消。切换 Vault 无法读取旧会话，补到的响应未创建旧账号 |
| 重授权使用错误地址、nonce、受众、签名或主体 | 原账号 ID、修订和可用凭据保留。正确重新授权延用原账号 ID |
| 并发续期、重启后再次续期和 `invalid_grant` | 同一账号的两个并发调用只交换一次。重启后的下一次续期使用上次轮换的 refresh token。永久失效后提示重新授权。公开账号和 Vault 文件没有测试凭据明文 |

## Lead 装配与未联验条件

1. 从 `@huhu/plugin-mail/engine` 导入 `createMailOAuth`。在真实 Engine 的进程内收集 `MailOAuthClients`，再传入 `mail.apply(ctx, api, owner, transport, syncOptions, createMailOAuth(clients, { hostLabel, openBrowser }))`。`syncOptions` 保留 S5 通知配置。`hostLabel` 填写会打开浏览器的 Engine 主机显示名。未提供某一客户端 ID 时该提供商显示未配置。
2. `openBrowser(url)` 通过现有受信任的主进程浏览器能力在 Engine 所在机器打开系统浏览器。宿主校验精确的 HTTPS host 和 path，仅允许 `accounts.google.com/o/oauth2/v2/auth` 与 `login.microsoftonline.com/common/oauth2/v2.0/authorize`，拒绝自定义端口、用户信息和其他目标。通过受信任的 Engine 配置提供 `google.clientId`、按桌面注册需要提供 `google.clientSecret`，或者提供 `microsoft.clientId`。个人和组织账号均需支持时，Microsoft app registration 使用 `common` 适用的账号类型并允许公共客户端，注册 `http://localhost/mail/oauth/callback`。Microsoft loopback 回调匹配允许临时端口。 [Google 桌面 OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) · [Microsoft 回调注册](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)
3. 在装配版本验证桌面 Workbench 打开实际系统浏览器并回到原 Vault 账号，补已授权 Google 和 Microsoft 测试客户端的联验。真实 Gmail restricted scope、Microsoft 租户 consent、个人 Outlook IMAP 和 Exchange SMTP AUTH 开关由实际注册与账号配置决定。本次测试替代了浏览器启动和在线提供商，仅使用回环 issuer、合成账号和本机隔离 Vault。

## 桌面宿主联验

Electron Engine 从部署方提供的 `HUHU_MAIL_GOOGLE_CLIENT_ID`、可选 `HUHU_MAIL_GOOGLE_CLIENT_SECRET` 和 `HUHU_MAIL_MICROSOFT_CLIENT_ID` 读取客户端配置。授权 URL 经私有消息交给当前 Vault 的主进程。主进程只接受 Google、Microsoft 对应的 HTTPS 授权端点和约定的本机 PKCE 回调，并回传浏览器打开结果。客户端资料只在宿主配置中提供。 [Google 桌面 OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) · [Microsoft 回调注册](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)

Windows Electron 实测用合成客户端进入等待状态，检查主进程实际收到授权地址及 S256 参数。测试接管最后一步的系统浏览器调用，避免发起在线登录。回环回调拒绝缺少 state 的请求，取消后原端口停止监听。Mail 五项 Playwright 测试通过。在线 Google 或 Microsoft 体验另需已注册的桌面客户端和授权测试邮箱。 [桌面验收用例](../../../../../../../tests/e2e/workflows/mail.spec.ts)
