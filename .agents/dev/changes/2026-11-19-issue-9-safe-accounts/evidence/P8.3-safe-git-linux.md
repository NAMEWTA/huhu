# P8.3 · Linux Safe 整代 Git 同步证据

基线为 `f7901b0a6b86910f52d74efac8ec1f438b387a9d`。验证使用 Node 24.21.0、pnpm 12.10.1、Git 2.53.0、临时 Vault、合成字段与本机 bare Git 仓。认证回归使用回环夹具。

用 `pnpm exec vitest run --maxWorkers=1 plugins/versioning/test plugins/safe/test` 重跑。最终单 worker 实测 12 个文件和 111 个用例通过，其中包含 5 个新增 Git 场景。测试同步信号改为复用项目现有夹具后，这 5 个场景再次通过。新用例在 [safe-sync.test.ts](../../../../../plugins/versioning/test/safe-sync.test.ts)。

| 场景 | 观察结果 |
| --- | --- |
| 自动同步与 Safe 写入交错 | 暂停标签密文写入，启动 `runAutomatic("sync")`，等待 Safe 写队列；远端尚无分支。放行后读取 bare 仓，用 `git ls-tree -rz` 检查完整组，用 `git cat-file blob` 逐个字节比较包装 keyring、清单及两种引用密文。Git ignore 和 clean filter 未改写 Safe blob，合成个人标记未出现在这些对象中。 |
| 排除与用户暂存 | 预览列出整组；排除一个密文时整组跳过并提示原因，普通文件依然可发布。已经跟踪整组时拒绝该次推送。未引用密文、旧元数据、审计、机器钥匙、ASKPASS、执行环境和缓存均未进入新树；允许的规则定义进入新树。既有用户暂存的 blob 与其工作区版本分别保留。 |
| 已跟踪旧资料 | 源端新树移除不再引用的密文和白名单外的旧项。源文件与已公开的旧提交仍可逐字节读取。把白名单外材料放进仅本地的旧提交后，清洁的候选 tip 仍无法推送：检查发现旧提交也会随历史发送。 |
| 分支冲突 | 两侧相同数字修订生成不同标签密文。同步返回 `GIT_CONFLICT`。本地和远端提交及各自 blob 保留，工作区与索引无合并残留。重建同步实例后仍显示整代冲突，逐文件解决被拒绝，自动同步暂停。 |
| 拉取 | 首次拉取后用原主密码解锁。已验证的快进切换到完整的远端代；未跟踪的本机旧原件和以前的 Git 对象仍可读。随后模拟远端删除一个引用密文，拉取拒绝且本地 HEAD 与当前密文原样保留。 |

## 集成与边界

- 真实夹具向 `VaultSync` 注入 `safe.safeGitSnapshots(files)`，与 Safe 写入使用同一个 `VaultFiles` 对象。Lead 在 `apps/engine/src/boot.ts` 的 Versioning 注册处通过 `VersioningOptions.safeSnapshots` 注入 `safe.safeGitSnapshots(api.vault.files)`，并保留同一 options 内的已有 `credentialHost`。
- 同步覆盖计划任务与手动调用的 `sync.run`，以及 `sync.preview`。已有普通 Git 冲突的解决回归通过。分歧分支若 Safe 组不同（含只有一侧改变 Safe 的分歧），保守地保留双方并报告整代冲突。整组选边提交留待后续。
- 成功快进时 Git 会按已验证的远端树更新受跟踪的当前 Safe 路径，已被替换的受跟踪密文仍存在于旧提交中。源端暂存清理保留工作区原件。现有提交、已在远端的旧对象以及旧数据包均无自动改写。手工 `git.stage`、`git.commit`、外部 Git 和回滚入口各有既有行为。
- 在锁定状态可检查外层结构、keyring 与清单标识、引用集合和密文封装。现有 Safe 解锁和读数据负责认证。跨进程写者、独立 Git 写入、其他平台和端到端桌面交互需要另行验证。
