# T7.1 定时终端发生的中断恢复

审查基线为 `311ba0c82839f627018695f8651541c8ff63ad71`。写入故障探针在该基线复现了问题。第一次写入运行文件失败后，重开的 Activations 已有计划点，但没有对应运行，调度器会跳过该点。

## 持久化和恢复

- 规则 ID 和 UTC 计划点决定运行 ID、发生 ID 与原启动请求 ID。定时终端以 `automation-run` 为持久记录，Activations 直接读取该记录。首次写入前中断时，现有调度器按规则启用或编辑时间及补跑宽限补交最近的合格计划点。
- 归属匹配且有未提交标记时，重开后的对账会比较规则文件版本、Space ID 及修订号和受保护环境的可移植定义，再走原启动入口。指纹只记录摘要。配置无法核对时，原运行显示待核对。
- 调用 Core 前先写入提交边界。即使引擎在此后、发出调用前结束，也只核对原 requestId 及已知 sessionId。未找到证据时显示待核对；查实后同一运行和发生更新为原会话结果。
- 历史 NDJSON 的完整行继续可读。当前终端规则的孤立发生显示待核对，并保留该计划点。其他 Vault 的未完成运行保留原文件，查询显示待核对，运行详情隐藏其他 Vault 的会话入口。

## Windows 验证

Windows x64 10.0.26300、Node 24.21.0、固定 pnpm 12.10.1、Vitest 3.2.7。故障探针向两个写入边界及启动服务注入中断，随后在同一临时 Vault 上新建仓储和服务读取真实文件。真实 Core 回归使用 0.1.19，二进制 SHA-256 为 `8c5c088eda5c441502fa58714277a250e38103c66180376ef00d63d6cab03f8d`。

Automations 和 Windows 本机保护合计 70 项通过。Engine 入口定向回归 3 项通过。Automations 与 Contracts 的 TypeScript 检查、改动源码的 lint 和格式检查通过。

| 检查 | 观察结果 |
| --- | --- |
| 运行文件写入前、提交标记写入前 | 首个计划点按原预留 ID 补交。已写入的运行在配置匹配时沿用原运行、发生和 requestId，只启动一次。 |
| 标记落盘后、Core 确认缺失 | 确认缺失时先显示待核对；只匹配原 requestId，恢复原会话结果。覆盖标记后尚未发出调用、Core 已创建但 sessionId 未写回、受保护启动包装错误和连接中断。 |
| 同槽、旧日志、归属 | 同一服务与同进程的第二个仓储实例争用时只有一个持久运行；旧日志孤立发生及半行保留原字节；其他 Vault 的已提交和未提交记录都不触发对账或启动。 |
| 配置及相邻行为 | 规则修改、停用、Space 修订和受保护环境修订都阻止恢复启动。提醒、手动终端、Agent 规则受理、旧格式工作台入口和 Windows 本机保护用例通过。 |

复跑入口如下。为本机保护回归将 `HUHU_AGENT_LAUNCH_TEST_BIN` 指向上述 Windows Core 二进制。

```powershell
pnpm --config.offline=true --config.verify-deps-before-run=false exec vitest run --no-cache --pool forks --maxWorkers 1 apps/engine/test/engine.test.ts -t '恢复 Engine 时只查询|旧规则环境|Agent 任务自动化的预览'
pnpm --config.offline=true --config.verify-deps-before-run=false --filter @huhu/plugin-automations --filter @huhu/contracts run typecheck
```
