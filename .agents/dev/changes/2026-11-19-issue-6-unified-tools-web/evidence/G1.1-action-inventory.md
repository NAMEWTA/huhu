# #6 G1.1 · 能力动作、真实入口与授权盘点

基线为 `impl/huhu-issues-3-10-capability@bf3942e456c03cd7a4a4070e230557bb45e1ca9c`。与主目录的 G1.1、source、spec、design、plan 逐文件核对哈希一致。本页的「现状」取自该基线。目标 scope、risk 和缺项指向后续切片。 [任务](../tasks/G1.1-action-inventory.md) · [规格](../spec.md) · [设计](../design.md) · [计划](../plan.md)

## 结论

- 基线有 **209 个 Engine 能力定义**。9 个内置插件合计 159 项，Kernel 50 项。56 项的 `exposable=true`，其中 27 项默认开放。G2 的目标是所有外部能力首次关闭，已认证桌面保留管理入口。当前停用只剩 ID 和 owner，`includeInactive` 用 `read/null/null` 填充。清单漏声明的 6 项在插件从未启用过时连 ID 都没有，见下表。
- `agent.core.status`、`agent.sessions.output`、`health.run`、`health.exportDiagnostics` 的当前 read handler 均可启动 Core。**退回 Agent CLI 与 Engine 健康诊断所有者改为 peek / 已有输出，以及显式启动或探测。** `agent.sessions.list` 和 `agent.history.list` 走不启动 Core 的对账路径，会更新已有运行投影。纯查询应消费投影，发布对账继续由领域所有者负责。
- SFTP 列表和预览要求已连接的主机，调用会打开、关闭 SFTP 子通道并写审计。对远端文件内容为 read，当前却注册为 execute。上传和下载依赖 Engine 机器路径，浏览器设备传输及独立流权限待补。受管文件的修改先确定领域 owner，并交给原有版本和写入机制。
- 可信运行回执、内部派发标记、进程心跳以及 Vault 文件监听回执留在内部。用户可见的是运行、等待、回复、取消、重试与结果查询等业务动作。

## G1.2 / G2 最小公共合同

1. **同一份能力声明，分别登记描述和执行函数。** 延伸现有 `defineCapability / CapabilityRegistry`。静态 descriptor 固定 `id, owner, title, description, scope, risk, input, output, visibility`，以及必要的读写、破坏性、外部交互和重试语义。保留 Zod 单源，发现工作采用 `toJsonSchema`。调用用同一个 ID 绑定 handler。装配验证重复 ID、owner 与 handler 是否匹配、清单覆盖、协议名称映射；停用卸 handler、保留 descriptor 和选择；卸载移除已安装目录的项。取消把停用项补成 read 的做法。 `visibility` 只分用户与内部生产者，用户高风险操作沿用可明确选择的偏好。
2. **一份按 Vault 存储的显式开放策略。** Kernel 的策略所有者复用 `ExposureStore` 的按 ID 偏好模型，用独立策略文件避免与插件启停的读改写互相覆盖。最小快照为 `revision` 和 `selectedById: Record<ID, boolean>`。缺 ID 表示未配置，false 明确关闭；新 Vault 默认皆禁用。损坏保留原字节，失败关闭外部授权并返回可机读错误。以 [VaultFiles.write](../../../../../packages/vault/src/write.ts) 的版本/同目录原子写能力为可复用基础。G2.2 在一个写者过程核验 expectedRevision、目录版本、全部目标 ID 和意图键，一次写并只在成功后发布一次变更。仍由现有插件存储拥有插件启停。
3. **一个纯判定投影，实际调用重判。** 依赖是由适配器认证的主体/入口、当前 Vault、静态 descriptor、有效 handler/插件、入口服务状态、当前外部策略和调用者原有的委托权限。区分 unknown ID、owner 未安装/停用、handler 缺失、入口关闭、内部动作拒绝、未配置/明确关闭、策略损坏和业务前置条件不足。MCP 两种传输再核各自入口状态，CLI/API 共用选择，受邀 Web 与桌面是工作台用户的独立身份。诊断基于已知快照，资源归属/动态前置条件交实际 owner，检查不启动 Core、连接 SSH 或执行 handler。管理目录看全量用户描述与解释，协议发现只看有效可调用描述，调用和资源/流重新计算同一规则。
4. **执行、输出和恢复继续走 Dispatcher。** 保持输入验证、主体和 request ID 透传。G3 用相同输出 schema 回读结果，明确输出验证失败或取消超时之后的未知状态。稳定意图键和操作 ID 绑定 Vault、认证主体、能力与规范化输入，以领域权威结果对账。当前按 caller 类别缓存幂等、admin 没有意图守卫，不能宣称跨会话或副作用后的结果已去重。扩展的通用代理按所选真实命令复验原主体，受信的一段内部业务委托继续用其权限组。
5. **下游交接。** G1.2 先用开/停/重开样例核对真实 schemas、owner、scope/risk 和重复注册失败。G2 补新 Vault 零开放、重启保留、损坏和批量冲突、check 无副作用、旧名称失权以及内部委托保留。Agent/Engine 先修正已列出的 read 副作用；SSH 局部资源选择仍按设计 Q6-3 决定，连接状态/用户资源归属始终由 SSH 校验。G4 和其余可见交互继续使用实际确认的原型版本。
