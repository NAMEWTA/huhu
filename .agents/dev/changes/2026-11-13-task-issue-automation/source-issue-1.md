## 1. 目标：一条任务、一份执行配置、一条评论时间线、三个任务状态

> 任务负责做什么、由谁做、在哪里做；自动化负责什么时候派发；Agent 执行并把问题和结果追加回任务；用户最后关闭完成。

任务模块应成为当前 Vault / 工作台各模块共用的工作派发与处理入口，而不再只是一个二态 Todo 清单。

- **Todo**：快速记录、开始、完成自己的工作。
- **Issue**：描述目标、配置执行者、持续讨论、处理请求、查看执行结果、关闭或重开。
- **看板**：同一批任务按状态展示，不是另一套存储或另一套执行系统。
- **模块协作**：自动化、Agent CLI、提醒及其他插件可以通过公共能力创建任务、追加评论、查询状态或关联来源。

本期不扩张为跨所有 Vault 的云任务平台，不做完整 GitHub 同步、多人组织权限、任意工作流编排或新 Agent 框架。

## 2. 最终产品模型与明确不采用的设计

| 维度 | 本次需求 |
| --- | --- |
| 执行类型 | 只有 `human`、`agent`。这是类型，不是标签，也不是状态。 |
| 任务状态 | 只有「未开始」「进行中」「已完成」。 |
| Agent 运行配置 | 属于任务：工作目录、Agent CLI、可选模型 / 推理强度等。 |
| 任务正文 | Markdown 的 `# 任务内容` 章节。 |
| 关联文档 | Markdown 的 `# 关联文档文件` 章节，使用当前 Vault 的相对位置。 |
| 评论 | 人、Agent、系统围绕同一任务持续追加。 |
| 需要用户操作 | 原任务的提醒标记、评论卡片及操作入口，不是第四种任务状态。 |
| 完成 | 由用户主动关闭完成，Agent 成功返回不自动关闭。 |
| 自动化 | 只保留 Agent 执行、终端命令、提醒三类。 |

### 2.1 状态、运行结果和注意力提示分开

以下组合都应成立：

```text
类型：Agent
状态：进行中
提示：需要你回答一个问题
```

```text
类型：Agent
状态：进行中
提示：Agent 已返回结果，请查看
```

```text
类型：Agent
状态：进行中
提示：上次执行失败，可查看原因并重试
```

等待输入、运行成功、执行失败、结果未知属于执行事实或提示，**不再新增「阻塞」「待验收」「失败」等任务状态**。用户回答问题时也不需要把任务类型从 Agent 改成 Human。

内部可继续使用已有运行状态，例如 `queued / running / waiting_input / succeeded / failed / cancelled / unknown`，但不能把它们直接扩展成任务看板列。

### 2.2 取消早期方案中的冲突项

- 不采用 `work / action_required / reminder` 作为三种任务类型；提醒或交互请求是来源 / 用途，不替代 `human / agent`。
- 已有关联任务时，不为每次 Agent 提问、确认或通知另建一条 Task。
- 执行已有任务时，不把目录、CLI、模型移到自动化里作为另一份可覆盖配置。
- 默认批量派发是逐任务使用各自配置，不把不同目录、不同 CLI 的任务合并给一个 Agent。
- 普通评论、保存任务、切换执行类型，不自动启动进程。
- 不把「Agent 返回成功」等同于「任务已完成」。

### 2.3 关于原先提到的标签

以最新补充为准：`human / agent` 使用明确的类型字段，不使用 tag 表达。

项目 / 主题标签及原先提出的多选标签筛选可以作为附加分类与筛选能力，但不是派发身份或授权。本期不为了两个执行类型另建复杂标签平台。若保留多标签过滤，需要明确「全部匹配 / 任意匹配」语义，建议默认全部匹配；预览和实际执行必须一致。

## 3. 任务创建、配置与状态流转

### 3.1 在任务内完成 Agent 配置

选择 Human 时，只需填写任务内容及普通任务属性。

选择 Agent 时，在任务表单内展开：

```text
工作目录       [选择已有目录] [选择本地目录]
Agent CLI      [选择已检测到且支持本次执行方式的 CLI]
模型           [可选]
推理强度等     [仅在该 CLI 支持时显示]
```

复用已有 Space、目录选择、Provider 检测、模型能力与启动配置；不建立第二份工作目录管理器或 CLI 配置库。界面可以使用「工作目录」这个直接的名称，底层继续使用既有 Space。

任务表单应能完成目录选择及必要的 Space 创建 / 关联，避免强制用户先跳转到其他模块配置后才能返回。

约束：

- 保存任务不启动 Agent；新任务默认未开始。
- Agent 任务进入可派发状态前必须有有效目录与 CLI 配置；无效配置应明确报错或显示不可派发原因，不能静默回退到当前目录、Vault 根或其他 CLI。
- 目录决定进程的工作位置；关联文档只提供资料，两者不互相覆盖。
- 已开始的运行冻结本次目录、CLI、模型、任务输入及相关版本。修改任务配置只影响后续明确派发，不修改正在运行的现场。
- 任务类型只有一份权威值。现有 `execution.kind` 与拟采用的 `type` 属于同一概念，统一契约即可，禁止两份可独立写入的类型字段。
- `completed` 如仍用于界面计算，只能从状态派生，不能与 `status` 双写并各自生效。

### 3.2 状态流转

| 事件 | 任务状态 | 对用户的表现 |
| --- | --- | --- |
| 创建 Human / Agent 任务 | 未开始 | 显示任务与创建记录，无进程启动 |
| 用户开始处理 Human 任务 | 进行中 | 显示开始处理记录 |
| 自动化正式接受派发并建立执行记录 | 进行中 | 显示派发记录及运行入口 |
| Agent 请求回答 / 确认 / 手动操作 | 进行中 | 原任务追加请求评论，显示需要用户操作 |
| 用户回答并继续 | 进行中 | 记录回复及发送 / 继续结果 |
| Agent 返回结果 | 进行中 | 追加结果评论，等待用户自行关闭 |
| 已派发运行失败 / 结果未知 | 进行中 | 明确展示结果，不被扫描器自动反复重启 |
| 用户关闭完成 | 已完成 | 记录关闭；用户也可直接关闭未开始任务 |

「派发」不能只表示查询命中了任务。建议采用现有 claim / run 路径：

```text
校验任务、目录与 CLI
→ 取得唯一处理权
→ 持久化执行记录
→ 任务进入进行中
→ 启动或进入执行队列
```

预检失败时保持未开始并显示原因；正式接受派发后的启动失败则保留执行记录和失败事实。跨记录更新必须有恢复 / 对账路径，不能出现启动了两个进程或永久显示已开始但没有任何运行依据的情况。

### 3.3 关闭、重开、停止与修改

- 关闭完成由用户决定，不依赖 Agent 结果，也不等价于批准命令。
- 关闭任务不隐式终止活动进程。存在运行时，应明确提示并提供独立的停止操作；尚未派发的已完成任务必须被扫描跳过。
- 关闭后收到晚到结果，只追加到原任务，不自动重开。
- 重开前检查是否仍有活动 / 等待输入 / 结果未知的运行，不能借重开重复启动。建议：仍有原运行时保持进行中；没有活动运行时回到未开始，新的派发意图由现有输入版本 / 处理记录机制明确表达。
- 看板拖动与列表 / 详情修改的是同一任务状态。单纯拖动或编辑状态不应隐式批准请求或向终端发送输入。
- 编辑进行中的任务或切换类型，不应自动中止 / 替换原执行；应显示本次运行使用的是哪个配置快照。

## 4. Markdown 文件约定

### 4.1 两个明确章节

任务仍是可用普通编辑器阅读和修改的 Markdown 文件。字段名称在实现时按当前 contracts 统一，以下仅示意内容结构，不把示例当成现有 schema：

```markdown
---
huhu:
  kind: task
  id: task_example
  schema: 2
title: 整理接口文档
type: agent
status: not_started
execution:
  spaceId: space_example
  provider: codex
---

# 任务内容

整理新版接口说明，列出与旧版的差异。

## 验收条件

- 给出输入、输出与错误处理说明。
- 保留差异列表供用户检查。

# 关联文档文件

- vault/设计/接口说明.md
- vault/设计/旧接口/
```

- `# 任务内容` 是任务要求的唯一正文来源。
- `# 关联文档文件` 是关联资料的唯一可编辑来源。
- API / 索引可以返回解析后的 `resources`，但不能再有一份独立可写的 frontmatter 关联列表与章节竞争。
- 界面编辑必须写回同一文件；外部修改也必须被识别。
- 其他用户章节、未涉及的字段和文本必须保留，不能保存一次任务就被重排或清空。

### 4.2 解析与路径

复用现有 Markdown / frontmatter / 文件服务能力，必要时小范围适配：

- 按真实 Markdown 标题边界解析，忽略代码围栏中的同名标题；支持章节内二级、三级标题。
- 必需章节缺失、重复、无法可靠解析时，显示具体文件问题并阻止自动执行，不能猜测正文。
- 约定 `vault/` 表示当前 Vault 根的逻辑前缀，不是系统绝对路径，也不是相对于任务文件所在目录。
- 支持 `vault/xx/xxx.md`、文件夹和能够唯一定位的无扩展名写法；歧义或不存在时明确提示，不能擅自关联同名文件。
- 规范化相对路径，校验越界和符号链接逃逸；不能把这种路径校验宣称为 Agent 的系统级文件沙箱。
- 关联文件夹默认只提供资料入口，不无上限递归读取整个目录。实际注入 / 读取的内容应有范围和容量控制，并记录到本次输入快照。
- 文件移动 / 重命名优先复用既有身份与索引能力；失效关联明确显示，不静默换目标。

### 4.3 任务要求、资料与评论分开

任务要求是授权范围内需要完成的工作，关联文档是上下文资料，不允许通过资料中的文本扩大执行权限。

评论在界面上显示在任务下方，不要求把所有讨论塞入 `# 任务内容`。优先复用现有 `Comments/` Markdown 存储，按任务稳定 ID 关联。正文、评论与运行日志各有归属，不能让 Agent 自己追加一次结果就修改任务输入版本并触发循环执行。

## 5. Issue 式评论与人机协作闭环

### 5.1 任务详情

任务详情应能连续阅读：标题与类型 / 状态、任务正文、关联资料、评论与系统活动、运行记录、当前待处理请求。列表、看板及详情反映同一数据。

典型过程：

```text
用户创建 Agent 任务并配置目录与 CLI
系统：自动化已派发本任务，状态变为进行中
Agent：发现两套接口定义，请确认以哪套为准 [需要你操作]
用户：以新版为准，旧版列出差异 [回复并继续]
系统：回答已发送，继续原会话
Agent：整理结果如下…… [查看结果]
用户：检查通过 [发表评论并关闭完成]
任务状态变为已完成
```

评论允许用户在任务派发前后持续补充，不应只能在 `waiting_input` 时发言。

### 5.2 明确区分操作

| 操作 | 语义 |
| --- | --- |
| 发表评论 | 保存讨论或补充说明，默认不启动 Agent，不向终端输入 |
| 回复并继续 | 绑定一个当前有效的问题，保存回复并调用已有回答 / 续跑能力 |
| 前往处理 | 聚焦原会话 / 原终端 / 对应结构化交互面板，由用户处理权限、登录等操作 |
| 关闭完成 | 只改变任务完成事实，不批准请求、不隐式杀进程 |
| 发表评论并关闭完成 | 保存评论并关闭，仍不代表执行授权 |

普通评论不自动触发新执行。需要送给 Agent 的讨论，通过明确的回复 / 发送动作纳入本次输入；开始执行时记录使用了哪些讨论，不能无差别把系统状态、Agent 自己的旧结果和所有历史评论当成新的工作指令。

### 5.3 评论的来源与可靠性

- 至少区分人、Agent、系统来源，显示时间；Agent / 系统身份由受信调用上下文确定，不能只信请求体中的作者名称。
- Agent 请求评论关联 task、run、问题 / 原生请求标识、原会话和可执行的操作入口。
- 任务卡片显示需要操作数量 / 提示，点击能直接定位对应评论或现场。
- 请求状态以运行 / Provider 的真实记录为准；评论是任务中的表达，不能成为另一套相互矛盾的审批状态机。
- 同一事件重发、应用重启或连接恢复时，不重复追加同一系统 / Agent 请求评论。
- 用户回复已保存但未送达时，显示「未送达 / 可重试」；重试不能重复续跑或重复批准。
- 已解决 / 过期请求明确显示，不保留可误点的旧审批按钮。
- 「已读」「已回复评论」「任务已关闭」均不自动代表 Provider 请求已经解决。
- 密码、登录令牌、密钥等不能落入任务正文或评论。
- 评论并发追加、外部修改与版本冲突使用现有写入和并发控制路径处理，不能覆盖他人或 Agent 的新评论。

### 5.4 复用现有批注与回答能力

现有 `CommentsService` 已有文件级评论、Markdown 消息、回复、解决 / 重开，但其身份解析仍与 notes 耦合；现有任务 `RunRecords` 已调用 `automations.runs.answer`。

本期优先：

1. 在已有评论实现上支持任务目标，使用任务现有稳定 ID，补齐来源与请求关联。
2. 把已有提问、回答和续跑能力接到任务评论区，不重新实现另一套问答后端。
3. 仅在实际依赖需要时提取公共评论部分；注册与生命周期一并调整，避免 tasks 为了评论被迫依赖 notes 启用，也避免直接导入 notes 插件内部实现。
4. 复用已有 Markdown 渲染和评论组件，增加任务所需的时间线呈现，不为任务强行引入正文锚点功能。

## 6. 自动化严格收敛为三类

| 类型 | 职责 |
| --- | --- |
| Agent 执行 | 定时派发已有 Agent 任务，或在不关联任务时执行规则内提示 |
| 终端命令 | 在配置的工作目录与终端环境中运行明确命令 |
| 提醒 | 投递通知，或按选择发布到任务中心，或同时投递 |

「按条件选择任务」是 Agent 执行的输入方式，不是第四类动作；「发布到任务」是提醒的投递位置，不是第四类动作。

### 6.1 执行已有任务

自动化规则负责时间、任务选择条件、补充指令和并发限制。目录、CLI、模型使用各任务自己的配置，不再在规则里保存冲突的覆盖值。

每次触发时重新查询，默认候选条件：

```text
类型 = agent
状态 = 未开始
符合规则的附加筛选条件
没有活动、等待输入或结果未知的冲突运行
执行配置有效且具备授权
```

- 规则创建后新增的匹配任务，应在之后触发时被选中。
- 保留筛选预览，展示将派发与跳过的任务及原因；预览不写文件、不创建 claim、不启动进程。
- 无候选任务时跳过并记录原因，不启动空 Agent。
- 多条匹配任务按各自目录和 CLI 分别派发；一次激活可以包含多条运行记录，不默认把任务合并为一个会话。
- 每条执行输入组合「该任务的内容 / 关联资料 + 自动化补充指令 + 本次明确纳入的讨论」，并冻结快照。
- 进行中、等待用户、Agent 已返回但用户尚未关闭的任务，不被下一轮定时扫描重新派发。
- 普通评论、提醒投递、系统状态评论不能造成重复派发。
- 同一计划触发被重复处理、两条规则选中同一任务、应用重启恢复等，复用已有 claim / 幂等 / 对账机制防止重复启动。
- 输入已变但原运行未结束时，不能用新输入绕过任务级活动运行保护。
- 失败或结果未知不自动重放；由明确重试或对账处理。对有副作用的外部进程，不宣称仅靠请求幂等就实现绝对 exactly-once。
- 并发限制复用现有实现；同一工作目录的冲突执行需要保护或明确提示，不另造分布式调度系统。

### 6.2 不关联任务的 Agent 执行

保留原「定时执行一段提示」用法，作为同一个 Agent 动作的另一种输入来源。

只有没有 Task 提供执行目标时，目录 / CLI / 模型才配置在规则里。需要人工响应且没有已有任务时，可按 §7 发布 Human 任务；不能因此恢复独立的第四种动作。

### 6.3 终端命令

- 用户能够配置工作目录、Shell / 终端环境、命令文本、必要的环境变量引用及超时。
- 复用现有终端 / Herdr / 会话能力启动，提供真实运行记录与终端查看 / 接管入口，不只是将旧 script 表单改名。
- 用户明确编写的 Shell 命令可以包含管道等 Shell 语义；任务正文、标签、文件名等外来数据不得未经处理拼接成命令。
- 已有程序路径 + argv 执行能力可作为内部实现复用；不能因界面简化而破坏参数边界。
- 运行中需要交互时保持原现场，不自动执行确认、不静默输入答案。
- 输出、退出结果、取消、超时与结果未知复用现有运行记录和监督机制。

### 6.4 提醒与发布任务

提醒的投递位置支持：通知中心、任务中心、两者。

发布到任务时，通过现有任务公共能力创建 `human` 任务，带上来源规则 / 触发标识 / 可导航目标；相同触发重试不重复建任务。提醒本身不启动 Agent。

其他模块同样可以通过任务公共能力创建任务；已有任务则优先追加评论或更新关联信息，不为了提示再创建一条重复工作项。任务自带的到点提醒与自动化提醒复用投递能力，不重复实现通知后端。

暂停规则只停止未来触发，不隐式终止已开始执行。关闭窗口、停止 Engine、插件停用和已存在终端的生命周期必须与当前实现核对并明确展示，不能承诺没有后台运行主体时仍能定时触发。

## 7. Agent CLI 运行中等待人的适配

### 7.1 处理现有能力的实际边界

当前自动化 worker 主要在 CLI 退出后，从最终输出回执解析问题并进入 `waiting_input`；这不等同于已经支持「进程仍活着，正在等权限、登录或交互输入」。

应先检查 huhu 已有 Provider、Herdr 客户端与会话接口，再检查 `temp/sources` 中对应固定版本的实现。对不能直接复用的部分才做小范围适配。

参考 Herdr 的状态上报、原终端聚焦与会话保活思路，但必须核对 huhu 实际集成版本和协议能力；不能把上游最新能力当作当前二进制已经具备。Provider 没有明确上报时，不能仅凭长时间无输出就断言正在等待批准。

### 7.2 统一用户体验，不假造统一底层能力

需要覆盖问题回答、权限确认、登录 / 认证和其他手动操作。

适配器应明确实际支持：能否报告等待、能否提供稳定请求 ID、能否在应用内回答、能否观察解决、能否打开原终端。

- 已有退出后提问：复用已有回答并 resume 路径。
- 支持双向结构化请求的执行方式：绑定真实请求标识处理回复 / 审批。
- 只能在交互终端处理的 CLI：评论提示并定位原终端，由用户操作。
- 无法可靠识别或程序化回答的情况：明确能力不足或提供人工查看，不伪造「批准」按钮。

不要求为了本期接入所有 Provider 协议或引入一个新的通用 Agent 运行框架。

### 7.3 有任务则回原任务，无任务才创建

```text
执行产生需要人的请求
→ 持久化到已有运行 / 请求记录
→ 已关联 Task：追加原任务评论并显示操作提示
→ 未关联 Task：必要时创建一条关联会话的 Human 任务
→ 用户处理原请求
→ 收到真实解决 / 继续反馈
→ 更新对应评论与提示
```

已有任务绝不因每次 blocked 状态变化重复创建新任务。独立 CLI 会话产生的 Human 任务也应关联来源，后续请求可持续追加，不无限刷任务。

### 7.4 保持原现场与防丢失

- 可见终端：聚焦 / attach 原 Space、原会话、原终端，不重启另一进程冒充继续。
- 无终端的结构化运行：打开实际交互面板，不能假装 headless worker 可以在阻塞后原地变成 PTY。
- 已结束会话：只通过明确的原生会话恢复动作继续，不自动恢复最近一次不相关会话。
- 事件去重优先使用原生请求 ID；没有时使用持久化的发生标识，不能只以「当前是 blocked」作为唯一键。
- 请求真实解决后清除需要操作提示；查看过、关闭任务或进程失联不能冒充解决。
- tasks 停用、Vault 暂不可写、应用重启期间，请求事实应留在既有运行记录中，恢复后可幂等补写评论 / 任务。不能只发一个内存事件然后永久丢失，也不因此引入消息中间件。

## 8. 插件能力统一复用：内外共用实现，权限分别控制

### 8.1 保留现有能力分发体系

```text
界面操作 ─────────┐
内部插件 api.call ┤
自动化 ──────────┼→ 现有能力分发器 → 同一业务实现
外部 CLI ────────┤
MCP / HTTP ──────┘
```

任务创建、查询、状态修改、评论追加、回答请求等能力，应能被有权限的内部模块与外部适配入口复用。

- 内部插件不通过启动 CLI、回连 localhost HTTP 或 MCP 绕一圈来复用业务。
- 外部 CLI / MCP 不维护第二套业务校验与存储逻辑。
- 跨插件业务操作不直接导入对方内部 Service 或写对方的私有文件。
- 公共能力契约、实现、输入输出、错误、版本冲突与幂等行为保持一致。

### 8.2 修正现有权限耦合，而非重建总线

当前 `Dispatcher.authorize` 对 `plugin:*` 调用也要求 `def.exposable`，而 Agent 的多项能力是不可外露的；部分业务 handler 还直接用 `caller !== desktop` 拒绝调用。

因此需要分别定义并核对：

1. 内部插件是否被授予调用某项能力的权限。
2. 能力是否允许对外暴露，以及用户是否开放了相应入口。

**内部有权调用不等于必须对外公开。** 不允许为了内部自动化能够调用，就把所有执行能力设置为外部可用。

仅修改 Dispatcher 还不够，要同步检查任务、自动化与 Agent handler 中的桌面专用判断，避免一处放行另一处拒绝，或简单删除检查导致外部越权。

### 8.3 创建 / 编辑任务不能成为执行授权后门

外部调用能写任务，不代表它能设置一个 Agent 类型或标签后立即获得命令执行能力。

区分写入工作项、配置 / 授权派发、真正执行这几种权限；来源和委托身份由受信上下文记录，不能由任意请求体自报。不得用「经过内置插件转发」抹去外部来源、扩大权限。

### 8.4 业务调用、事件、基础服务各归其位

- 要求完成操作并拿到结果：调用能力，例如创建任务、追加评论、回答问题。
- 操作提交成功后通知其他模块：发布事件。
- 文件、终端流、密钥引用等：复用受控基础服务。

不能广播一个「请创建任务」事件，就假设任务已经创建成功。进程内服务不应成为绕过业务权限的后门。

现有能力优先扩展：`tasks.create/read/update/list/setCompleted`、`comments.*`、`automations.runs.answer`、`agent.spaces.*`、`agent.providers.detect`、会话 / 终端能力。需要新增的方法，应先证明现有契约不足；方法名在规格阶段统一，不预设另一个任务后端。

插件停用 / 重启后，能力、订阅及界面贡献按现有作用域机制释放 / 恢复；任务基本操作不应因自动化停用而不可用。运行任务的执行能力建议快速返回运行标识，长期状态通过已有运行记录获取，而不是让一个业务调用一直等待整个 Agent 生命周期。

## 10. 强制执行复用优先原则

任何新功能或技术方案都必须按以下顺序评估：

```text
① Huhu 当前已有实现
         ↓
② temp/sources 中的成熟实现
         ↓
③ 现有成熟开源依赖或框架
         ↓
④ GitHub 上的优秀开源项目
         ↓
⑤ 基于成熟方案的小范围适配
         ↓
⑥ 确实没有合适实现时才自行开发
```

**禁止未检查现有实现，就直接设计或实现新的基础设施。**

执行要求：

- 对每个需要新增实现的缺口，记录实际检查的文件 / 符号、能复用的部分、不能直接复用的原因、最终适配范围与验证方式。
- 前层已能解决时，不为了调研数量继续引入替代框架。
- 没有权限、没有工作副本、文件不存在或暂时无法读取，记录为「未检查 / 不可获取」，不能记录成「无可复用实现」。
- 先复用现有业务及成熟依赖；只为确实缺失的领域行为增加小范围代码。
- 不新增并行事件总线、通用工作流引擎、分布式队列、第二套调度器、第二套终端运行时、第二套审批 / 问答后端或一套泛化评论平台。
- 参考源码保持只读；实际复制保留来源、提交和必要声明，更新现有来源台账与第三方说明。

- [ ] A01：任务执行类型只提供 Human / Agent，状态只提供未开始 / 进行中 / 已完成；列表、详情和看板使用同一事实。

- [ ] B01：用户可以在任务派发前后持续发表评论；普通评论不启动 Agent、不直接写终端、不改变处理版本导致扫描重跑。

- [ ] B05：前往处理打开原会话 / 原终端 / 对应结构化请求；不会新启动一个无关 Agent 冒充接管。
- [ ] B06：请求解决或过期后更新对应评论；已读、关闭任务、普通评论不能被解释为批准；敏感认证信息不落入评论。
- [ ] B07：同一请求重发、重连、重启不产生重复评论或任务；没有 Task 的独立会话按来源创建 Human 任务后可继续关联。
- [ ] B08：任务关闭后运行若仍在进行，界面明确显示；晚到结果不重开任务；重开不会重复启动仍活动的原执行。
- [ ] B09：评论并发写入 / 外部编辑不丢失消息；任务评论不因 notes 插件停用而失去必要的独立可用性。

### C. 自动化

- [ ] C01：创建 / 编辑自动化只看到 Agent、终端命令、提醒三类；旧四动作模型和无用产品分支不再生效。
- [ ] C02：执行已有任务时，目录 / CLI / 模型来自任务；无任务直接提示才在规则内配置目标。
- [ ] C03：规则创建后新建或修改筛选条件匹配的任务能在后续触发时选中；预览与实际查询一致，预览零副作用。
- [ ] C04：没有候选时不启动 Agent；进行中、等待用户、已完成及结果未知的冲突运行不会重复派发。
- [ ] C05：两条不同目录 / CLI 的任务分别使用自身配置；自动化补充指令与对应任务内容一起进入各自运行快照。
- [ ] C06：重复激活、两条规则竞争、重启恢复只形成有效的唯一派发；失败 / 未知不自动无限重试，仍可明确对账或重试。
- [ ] C07：终端命令有真实可查看现场；Shell 语义来自用户明确命令，外来数据不变成未经授权的 Shell 代码。
- [ ] C08：提醒可选择通知 / Human 任务 / 两者；同次提醒重试不重复创建任务，已有任务提醒不产生无必要的副本。
- [ ] C09：暂停规则不终止活动执行；Engine / 插件停用及恢复的行为明确，已存在的待处理请求不丢失。

### D. 插件复用与交付

- [ ] D01：内部插件和外部 CLI / MCP 对同类操作进入相同业务契约与实现；内部调用不绕经外部传输，也不直接写其他插件私有数据。
- [ ] D02：被授权的内部模块能调用不可外露的能力；同一能力的外部入口仍受单独的暴露与授权限制。
- [ ] D03：外部创建 / 编辑任务不能仅靠 `type: agent`、标签或自报来源绕过执行授权；普通评论不能伪造系统审批。
- [ ] D04：模块缺失 / 停用有明确错误和恢复提示，已持久化的待处理事实在恢复后能幂等补齐，不依赖一次性内存广播。
- [ ] D05：每个新增实现有复用检查依据；未读取的 `temp/sources` 不被记为已检查；没有重复基础设施。
- [ ] D06：代码、契约、示例、测试及原规格同步更新；不保留双写、兼容 / 迁移框架及已被否决的旧设计。

---

## 14. 完成定义

完成不是「多了几个页面和字段」，而是用户可以实际完成下面的闭环：

**写一条 Markdown 任务 → 选择 Human 或配置 Agent 的目录与 CLI → 自动化按时派发 → 原任务进入进行中 → Agent 的提问和结果持续追加到原任务 → 用户在原任务或原现场处理 → 用户关闭完成。**

其他插件、CLI 与 MCP 能在各自授权范围内复用同一能力；实现主要建立在 huhu 已有代码和成熟来源的小范围适配上。交付报告应区分已验证、仅静态检查与尚未验证的行为，不用假 CLI 的通过结果冒充所有真实 Provider 已支持。
