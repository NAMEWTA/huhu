# Mail OAuth 持久终态与待核实

继续复用 Mail 专用的 `OperationReceipts`。一条发起受理回执保留原会话 ID 并挡住相同请求键。物理 Vault 绑定的索引记录会话所属主体摘要及预分配账号 ID。有效回调在交换前持久登记进入交换。已知终态写入脱敏结果，其中成功包含原账号 ID 和原 SMTP 可用状态。已登记待交换的会话失去内存状态时，如缺少完成证据，返回同一 ID 的 `unknown / commit-unconfirmed`。

凭据事务将会话 ID 和有效 SMTP 选项放入同代本机加密凭据包。补查以索引指定的准确账号及 ModuleCredentials 当前发布代为准。只读凭据验证不刷新令牌，不用同地址或旧账号存在推断成功。凭据续期保留本机见证。普通 Vault 包继续使用原 portable definition，回执、加密见证及令牌不在其范围内。重复查询只读取结果。

## 本机 Windows 复验

`plugins/mail/test/oauth-engine.test.ts` 使用当前生产 Engine 路径、现有 Mail descriptor、真实 ModuleCredentials、签名回环发行方和合成账号。定向故障在真实凭据保存步骤前后介入，其余由现有流程执行。

| 观察点 | 实际结果 |
| --- | --- |
| 已配置后按同 ID、同键重开和停启 | 返回原会话、原账号及 `configured`。同键重交无新浏览器或交换 |
| 内存达到 32 个会话后的清理 | 清理前的旧终态仍能按 ID 与原键回读 |
| 升降 Vault、同逻辑 Vault ID 的物理副本 | 副本拒绝原会话。不同受信主体也无法读取旧 ID，当前 Vault 桌面可管理授权 |
| 交换挂起时停机，凭据未证实 | 原 ID 和原键都返回 `unknown`。同地址其他配置出现后仍然待核实 |
| 真实凭据已提交但终态回执写失败 | 重开前发起回执仅为 `accepted`。重开按已发布的同代凭据见证恢复原账号，按 ID 补齐终态，按原键复查，无新浏览器或交换 |
| 已有账号的重新授权在 definition 发布前失败 | 原账号修订保持。仅存在前一次授权凭据，原操作按 ID 和原键保持 `unknown` |
| 已证实的取消、拒绝与自然过期 | 分别回读 `cancelled`、`failed/denied`、`expired`。原账号、原授权材料边界及 Gmail／Exchange 既有回归通过 |

新版缺少可证实终态的旧受理回执保留原 ID 并返回待核实。明确的 Main 拒绝继续走现有等待中失败语义。真正系统浏览器迟到 ACK 仍需共享宿主区分「明确拒绝」和「通信结果未知」，后者保持原监听直至现有超时，不在本片改公共 Main 或 Engine。
