# S0.2 合成邮件传输取证

Windows x64 build 26300，Node 24.21.0。使用原工作区 `temp/issue-baseline/mail-protocol` 的独立锁与夹具，实际安装 ImapFlow 2.12.1、Nodemailer 10.6.0 和 MailParser 3.14.5。运行 `node probe.mjs`。Core `t39` 退出 0。IMAP、HTTP 和 SMTP 端点均绑定环回地址和临时端口，消息和账号均为合成夹具。

| 样例 | 实得结果 | 实施含义 |
| --- | --- | --- |
| IMAP 只读获取正文 | 选择只读 INBOX，读取 UIDVALIDITY 123。以 UID 42 发出 `UID FETCH` 和 `BODY.PEEK[]`，解析到 `IMAP body`。退出后连接数为 0。 | 本机消息记录需要账号、目录、UIDVALIDITY 与 UID。正文获取可独立于设置已读。 |
| API 原生字符串 ID | 回环 JSON fixture 以 `provider_id-01` 返回 MIME，解析到 `API body`。两条样例 RFC822 Message-ID 相同，正文各自保持正确。 | API 定位保留账号与原生 ID。该夹具验证定位与解析，不覆盖 Gmail 或 Graph 的实际协议与授权。 |
| SMTP 在正文发送后失去确认 | 服务端收到固定 Message-ID 的完整 DATA 一次并断开，客户端得到 `ECONNECTION`、`command=CONN`，无 SMTP 回包码。测试将 `probe-op-1` 原子写为 `unknown`。新的 Node 进程按记录读回同一 operationId、Message-ID 及状态，服务端仍只收到一份。 | 连接错误标签不足以判断邮件未送达。产品应冻结投递意图并保留结果未知，依据服务端证据对账后再决定后续动作。 |

本结果证明 TS/Node 库可承接三条代表性路径。生产权限、真实 IMAP/API 提供商、发送取消、发送前崩溃窗口、安装包依赖和 Rust 方案的实际对比仍待验证。候选库目前只在隔离测试使用，产品锁文件没有新增依赖。[ImapFlow 获取正文](https://imapflow.com/docs/guides/fetching-messages/) · [Nodemailer 错误参考](https://nodemailer.com/errors)
