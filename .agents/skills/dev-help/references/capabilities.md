# 开发能力地图

名称对应相互协作的技能。咨询使用[完整指南](guide-index.md)，跨阶段执行调用 `dev-workflow`，阶段明确时调用相应技能；专用工具仍以实际环境为准，技能安装不代表已具备浏览器、后台调度或外部账号权限。

| 技能 | 职责与可组合模式 |
| --- | --- |
| `dev-help` | 选择方法、解释调用方式、组织提示词、排查流程偏离 |
| `dev-workflow` | 协调跨阶段交付、接续后阶段尚不明确的任务；记录与复核任务决定及实际证据 |
| `dev-program` | 编排多个已有 Change，按真实依赖推进到整批验收，为 Goal 准备或接续批次 |
| `dev-handoff` | 保存开发上下文、准备跨会话交接、核对旧任务恢复点或执行明确暂停；沿用现有产物与记录 |
| `dev-issue` | 将想法、Bug、性能或重构诉求写成可认领的 GitHub Issue，更新正文或追加评论；按授权发布并回读结果 |
| `dev-intake` | 需求整理：把散落材料整理成来源、事实、目标、范围、已有决定与缺口 |
| `dev-grill` | 按依赖访谈，逐轮写入 `decisions.md` 或相应地图问题 |
| `dev-spec` | 综合已定共识，在 `spec.md` 保存行为与可观察验收 |
| `dev-plan` | 依据 `spec.md` 保存垂直切片、同名报告与 `plan.md` |
| `dev-sharpen` | 请求改写：用四问完善表达、目标、材料、方法与验证方式，交付提示词；实施由当前负责人推进 |
| `dev-architecture` | 从调用者用法确定类型、接口、模块与状态所有权，比较不同方案 |
| `dev-parallel` | 切片覆盖、竞速与多候选比较，隔离写入并综合验证 |
| `dev-worktree` | 创建、接手、审计和回收隔离检出，按顺序合并回直接父分支并验证 Git 拓扑 |
| `dev-merge-conflict` | 定位并解决在途 Git 冲突，核对双方行为和实际组合验证 |
| `dev-ui-design` | 统一产品界面、落地页和设计系统；在项目代码中使用 token、组件与状态，无需设计工具账号 |
| `dev-prototype` | 将已确认文档转成沿用项目风格的完整交互 HTML，取得并保留具体版本的用户确认；按需用探索分支回答未决问题 |
| `dev-build` | 按规格与适用的确认原型实施新功能、重构和视觉对齐；为既有正确行为补测，构建真实动作面板 |
| `dev-tdd` | 显式采用测试先行时，按公共接口逐行为红绿循环；在当前实现任务内作为方法使用 |
| `dev-debug` | 普通 UI、API、CLI 或 Issue 功能故障的真实复现、根因、修复与复核 |
| `dev-guardrails` | 对已识别的约束或反复错误建立类型、接口、状态所有权、lint 或 CI 防护 |
| `dev-review` | 行为契约与工程规范两轴检查、对抗审查、影响范围和有证据的发现；无 spec 文件仍审明确用户要求 |
| `dev-verify` | 真实入口与副作用验证，创建和维护项目专用验证方法与功能图 |
| `dev-formal-verify` | 选择属性与工具，建立代码映射，检查反例，维护模型与实现一致性；生成 `dev-formal-verify-<area>` |
| `dev-statechart` | 接收 TLA+/TLC 模型与结果，生成中文状态图；不变量违规可给最短图路径，时序反例保留循环轨迹，不直接接收 JS 模型 |
| `dev-benchmark` | 围绕延迟、吞吐和资源等指标完成测量、运行取证与优化，保留公平基线 |
| `dev-pr` | 创建、跟进或合并 PR，按实际依赖与授权推进队列 |
| `dev-deploy` | 将指定制品发布到目标环境，核对版本、业务结果和恢复状态 |
| `dev-learn` | 解释当前模块机制、组织教学或直接通俗复述；帮助接手和理解修改入口 |
| `dev-why` | 调查某项设计当时为何采用及历史约束；区分证据、推断与未知 |
| `dev-session-history` | 定位三种宿主中当前项目的会话 |
| `dev-recall` | 回忆近期工作并核对共享记录与现状 |
| `dev-reflect` | 根据指定对话改进开发方法 |
| `dev-archive` | 收尾交付，更新术语、背景、ADR 与错误经验，处理冲突和过时引用 |
| `dev-writing` | 完整技术写作标准、文档模式、清晰表达、PR 与提交说明 |
| `dev-status` | 只读书面汇报指定范围的进展、证据与待决事项 |
| `dev-status-video` | 根据真实素材制作进展视频并核对字幕、画面和停留时间 |
| `dev-skill-authoring` | 编写或修改项目技能，核对触发条件、包内资源和代表性场景 |
| `dev-personalize` | 从授权证据提炼稳定工作偏好，形成或修订个人模式 |
| `dev-issue-setup` | 初始化来源、身份、追踪器、仓库路由、UI 控制与实际触发能力，按来源配置报告监控 |
| `dev-issue-triage` | 对来源适配器或用户提供的报告分类、查重和分流；只依据已有证据，不运行复现或修复 |
| `dev-issue-fix` | 在可信分诊与真实 UI 控制前提下，仅复现、验证已有补丁，或完成授权的受限修复 |

运行声明要与证据相称。没安装专用技能不证明项目缺少同类能力；先检查既有脚本、验证代码、连接器与知识。形式化、测试、实际操作和静态约束互补，任何单项都不能替用户证明需求本身正确。

每次任务选择一个当前负责人，其他技能补充局部结果后返回。一个变更沿用一份权威行为契约，每个决定只写在一个位置，仍有效的验证证据直接引用；不因安装了多个技能而重复走完全部阶段。

完整原则正文见[原则指南](guide-principles.md)，注释处理见`dev-guardrails`（注释审查）。
