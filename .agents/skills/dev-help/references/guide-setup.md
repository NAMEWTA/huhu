# 接入开发技能并运行首个任务

确认技能已经安装后，从一个真实小任务开始。准备并行开发、创建工作树或运行构建与浏览器验证时，按任务所需核对运行条件和当前可用资源。

## 确认安装

本项目技能安装在目标项目的 `.agents/skills/<domain>-<name>/`，目录下应有 `SKILL.md` 及其引用资源。只检查用户选择的领域或技能，不把其他宿主目录当作额外安装目的地。

尚未安装时，使用当前技能源仓库实际提供的安装器及其帮助，或由用户指定的安装机制复制完整包。不能在未找到脚本时编造命令，也不能只复制 `SKILL.md` 而漏掉参考、模板和配套许可。已经能读取完整包时直接按任务使用。

宿主可能通过技能菜单、显式名称或读取 `SKILL.md` 使用技能。按 [宿主适配](harness-adapter.md) 检查实际行为；某个斜杠前缀或插件命令存在于其他环境，并不意味着当前环境也支持它。

安装时选中任意 dev 技能，安装器就一次性补齐 `.agents/dev/` 根、六类分区和 implemented/rejected 归档入口的九份短 AGENTS.md；选中 system 技能另补系统根说明。显式选择、领域选择和交互选择遵循同一规则，预览不写入，重复安装会补缺失并自动覆盖更新固定位置的模板说明，内容相同不重写。根 AGENTS.md 与业务记录不覆盖，不预填业务知识，不需要再调用技能建立骨架。按当前任务显式读取相关说明，不假定宿主递归自动加载。

## 核对运行环境与资源

需要环境信息时，复用 `.agents/dev/context/environment.md` 中适用于本次任务的运行条件、资源观测和已有预留。记录缺失、过期或执行主机变化时，对照项目的依赖与运行要求，按当前执行主机及用户指定远端的实际情况补查所需信息。

初次接入、换机或希望集中了解当前容量时，可以单独提出只读评估。已有记录仍有效时直接继续任务，不要求先建立环境报告。

```text
只读评估当前项目在实际执行环境中的容量，并更新已有环境记录。
先给包含主会话的建议 Agent 总数、当前可新增数、重任务并发和每项内部 worker，
再给指定状态的 worktree 保留量与依据。区分实测、估算和未知。
```

普通评估只读调查并写入所需报告，不自动安装依赖、构建、测试、批量启动会话、创建工作树或执行清理。只能看到当前执行器时，结论限于这个执行器；用户指定远端单独核对，不把远端和本地容量相加。

读报告时分别看会话、重任务和保留 worktree。会话总数包含主会话；安装、构建、测试和浏览器验证另占重任务名额，还要限制每项内部 jobs 或 workers。保留 worktree 的数量取决于纯源码、已安装依赖或含产物等状态；可保留更多目录不意味着可以同时启动更多重任务。

只有 1 个主会话且缺少新增会话样本时，应写“实际并发上限未知，暂无可确认新增名额”，并给出最小补测方法。新增量为 `0` 不表示机器最多只能运行 1 个 Agent。5 个并发通过只能称为“已验证运行规模为 5”，不能称为“实测最大上限”。

缺少某项负载的成本时，可在已经授权的任务中观测它：

```text
观察本次已授权的构建任务，记录当前 jobs 设置下的资源峰值和完成时长。
如果需要额外校准，先按余量确定最大并发、时长或轮次、停止条件及可用停止入口。
缺少支持下一档的证据时停止增加，并把结果更新到原环境报告。
```

校准优先复用正常工作，不同时放大多个未知负载；未覆盖关键峰值时保留未知，不把缺少样本当零成本。后续开发可以直接按记录安排：

```text
复用 .agents/dev/context/environment.md 的有效预算分批完成本次任务。
让现有 worker 接续多个 task，重任务按名额排队，每项遵守报告中的 worker 设置。
启动前检查实时余量与预留，过期部分按当前执行主机补查。
```

规划、派发与实施共享同一资源池的占用与预留。各 worktree 和 Change 引用同一权威记录，嵌套 Agent 使用父任务分配的预算。任务在依赖上可并行，不代表可以同时启动；切换 task 或压缩上下文不自动创建会话。需要多少个独立视角与同时运行多少个执行者分别安排。

余量不足或当前数量已经超过新建议时，新增量为 `0`，停止扩张并排队重任务，不抬高预算、不因等待超时而强行启动，也不因更新报告而擅自结束会话。会话退出后仍保留的服务和工作树继续占用资源；确需回收时，由 `dev-worktree` 按已有方法处理，实际释放后才更新预算。换机、依赖或 worker 设置变化、恢复旧会话和回收后，重新核对相关结论。

## 选择是否补齐验证

任务需要真实入口验证时，检查项目是否有应用驱动设施或验证技能。两者都没有时，只提出一次按 `dev-verify`（创建验证技能）补齐的建议。

用户已同意或已明确要求生成时，在其指定源仓库创建标准项目技能；安装目标仍是 `.agents/skills/`。该技能应能启动应用、诊断实例、驱动真实用户路径、保留证据并清理本次资源。交付前至少完整执行一次，才能称为已证明可用。用户不需要时继续当前任务；之后也可以独立补齐。

能检查真实结果的智能体，才有依据继续修复并达到完成条件。缺少驱动能力时，结果会频繁回到人手里检查。对经常开发的项目，优先补一条高价值真实路径，比仅增加流程文字更有用；不能因为工具不可得就假装已经验证。

任务涉及需要检查的形式属性时，使用 `dev-formal-verify`。行为测试覆盖实际运行的例子；模型检查或证明在明确假设与范围内检查某个属性，例如“一个作业不会同时运行两次”。并发、重试、状态转换或解析器中，若缺陷代价高且常规测试难触及，可选择一个属性。其余任务可以跳过，不把形式化工具变成每个项目的门槛。

说明实际验证范围，继续完成当前条件允许的小任务；只有宿主明确需要新会话时才告知相应操作，不为格式检查重启开发环境。

## 控制成本

子智能体和独立评审会增加调用成本。按任务风险使用它们：

- 缩短评审列表，让每个独立视角都有具体作用，不追求数量。
- 简单、明显的小改动直接处理；完整多阶段流程留给有实际风险或依赖的任务。

## 运行第一个任务

选一个真实但较小的目标，用普通话说清用户行为和不应改变的契约，例如：

```text
为这个命令添加 --json 标志。文本输出保持逐字节一致。验证两种输出。
```

把与任务匹配的实施步骤列入简短待办。完成、未检查和跳过应区分；跳过的步骤记录具体理由，让用户能看懂实际范围，不把未执行伪装成通过。

此后正常追问即可。若宿主支持持续技能模式，可以按真实界面使用；否则在任务记录中保留当前目标，并按需读取本地技能。不能假定某个键盘快捷键、菜单或“模式”在所有宿主存在。

完成首个任务后，留下实际验证证据及仍未覆盖的条件。准备把任务交给持续执行时，再读 [无人值守指南](guide-autonomous.md)。
