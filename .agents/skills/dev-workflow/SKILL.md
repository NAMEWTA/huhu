# 从需求到交付

先说清用户要改变什么、完成意味着什么，随后执行。把已授权的工作持续做完；需要决策时先完成不依赖该决策的部分。不要把“写了计划”“代码能编译”“已开启自动合并”当成最终交付。

## 工作约定

- 项目已有 `.agents/dev/context/model-roles.md` 时，按本次明确要求或项目选用的默认组应用角色和复核约定。未选用的组仅供以后使用，其余执行安排沿用当前工具。接续与交接传递同一任务的临时选择。
- 按目标、风险和反馈成本选择开发方法。可先写规格，也可在明确的公共接口上测试先行，或直接实现后验证；方法可以组合。始终明确可观察的完成条件，取得真实行为证据，不把某套流程强加给所有任务。
- 以当前代码、运行结果和实际发布制品描述“现在是什么”；以用户确认的目标描述“要变成什么”。发现差异就修正实现或过期记录，不能拿旧文档覆盖用户目标。
- 依据规模选择过程。小修改可把规格写成几句话；跨模块需求才拆切片、设计和记录。不要为每次编辑加载全部知识、建立固定审批链或填写空模板。
- 用户已经授权的范围持续有效。研究、实现、可逆验证不重复确认；外部发布按用户明确目标执行。仍缺生产目标或授权时，先把制品、差异、回滚和检查准备好，再说明缺什么。
- 本技能是编排入口，依赖下表的阶段技能。按当前任务调用对应入口，携带已有产物与返回条件；安装依赖不表示执行所有阶段。
- 一个任务由当前负责人持续推进。一个变更沿用一份权威行为契约，每个决定沿用一个记录位置；契约可以在已有 brief 或 spec 中逐步补全。调用时给出这些位置，专门方法补充所需部分后返回。已确认原型仍单独保存，作为覆盖范围内的可见效果与交互依据。
- 复用对当前代码、环境和范围仍然有效的验证证据；仅在条件变化或发现证据缺口时补验，不因阶段切换重复验证。

## 选择下一步

| 当前情况 | 推进方式 | 可调用技能 |
| --- | --- | --- |
| 不知道应该用哪个能力，或只想了解使用方法 | 按任务选择最小入口；先解释使用方式，不把咨询误当实施授权 | `dev-help` |
| 配置环境、角色模型、预算或项目协作规则组 | 核对真实可用工具和模型，沿用已有配置，不假定后台能力；默认目录骨架由安装器负责 | `dev-setup` |
| 想让重复工作逐步符合自己的习惯 | 从允许读取的历史中提炼稳定模式，形成简短可维护的项目技能 | `dev-personalize` |
| 要编写或修改项目技能 | 使用通用技能编写分支，明确触发、成果与场景检查；无需先提炼个人历史 | `dev-personalize` |
| 用户在任务中询问进展，或需要给人阅读的简报 | 汇总已完成、当前证据和待决事项；回答后继续原任务，除非明确要求暂停 | `dev-status` |
| 保存开发上下文、交给新会话、接手具体旧任务或明确暂停 | 保存交接文档或核对恢复点，再返回当前执行阶段；仅保存不停止工作 | `dev-handoff` |
| 需要把聊天、Issue、截图、日志或多处反馈整理成开发请求 | 整理来源、事实、目标、范围、已有决定与信息缺口 | `dev-intake`（需求整理） |
| 要配置报告接入或按来源监控需求 | 分开选择来源、追踪器、仓库路由、控制方式与实际触发器，完成授权内初始化 | `dev-issue-setup` |
| 需要对报告分类、查重或分流 | 沿用来源适配器或用户提供的单条材料，依据已有证据给出分类和去向；本阶段不复现或修复 | `dev-issue-triage` |
| 已配置报告管道，可信分诊和真实 UI 控制条件齐备 | 核对归属，按完整协议复现或验证已有补丁；需要且已授权时修复并交付草稿 PR | `dev-issue-fix` |
| 存在必须由用户选择、且会改变结果的产品取舍 | 先从代码回答事实，再按决定之间的依赖逐轮访谈，更新指定决策记录 | `dev-grill`（决策访谈） |
| 已有共识还不足以独立实施或验收 | 在既有权威契约中补齐行为、边界、非目标与成功条件 | `dev-spec`（行为规格） |
| 用户要深化或改写待执行的请求 | 用四问检查专业遗漏、原始材料、具体方法与独立证据，交付可使用的提示词 | `dev-sharpen`（请求改写） |
| 接手陌生模块 | 沿一个真实用例走通入口、业务、存储、反馈和失败路径 | `dev-learn` |
| 不理解历史设计为何存在 | 区分当前行为、当时理由和推测，追溯代码与可获得的决策证据 | `dev-why` |
| 边界或接口有实质取舍 | 比较不同结构；从调用方体验、状态所有权与领域术语判断 | `dev-architecture` |
| 已有或明确要建立 TLA+ 模型，需要带 TLC 检查结果的状态图 | 区分不变量与时序属性；不变量给最短图路径，时序反例保留循环轨迹，逐步核对真实代码 | `dev-statechart` |
| 需要检查关键属性、选择形式化工具或维护模型 | 明确属性、假设与边界，运行检查并识别模型漂移；仅 TLA+/TLC 结果交 `dev-statechart`，其他模型使用兼容的展示方式 | `dev-formal-verify` |
| 涉及页面、交互、设计系统或视觉验收 | 沿用实际代码中的组件与 token；按产品或营销场景读取设计规范，不要求设计工具账号 | `dev-ui-design` |
| 已确认文档需要转成可体验的整体效果，或新增布局/交互尚未经用户确认 | 复用项目视觉基线，生成完整交互 HTML、走查并记录具体版本的真实确认；探索模式只解决未决问题 | `dev-prototype` |
| 已有多个独立 Change，需要安排先后、放入 Goal 或接续整批开发 | 引用成员记录，判断跨 Change 的交付条件与整体验收 | `dev-program` |
| 需求无法一次可靠交付 | 拆成可验收的垂直功能切片，显式依赖，先跑通最小完整链路 | `dev-plan` |
| 已选择并行分工或需要比较候选方案 | 分配写入范围和验收规则，再集成并验证最终结果 | `dev-parallel` |
| 规格或切片已具备实施条件 | 核对适用的原型确认版本与范围，按既有工程规范实现，接通真实行为，验证当前制品 | `dev-build` |
| 需要复现、定位或修复 CLI/API/UI 功能错误及验收失败 | 沿实际入口建立证据并定位根因；Issue 只是来源，仅以性能指标为目标时进入测量流程 | `dev-debug` |
| 用户指定测试先行，或当前实现已选择 TDD | 按公共接口逐个完成失败测试与最小实现；已有正确行为补测不自动进入红绿实现 | `dev-tdd` |
| 同类错误反复出现或关键约束容易被绕过 | 优先改善类型、接口与状态所有权；有真实价值时增加可执行规则 | `dev-guardrails` |
| 需要审查实现 | 对照权威契约或明确用户要求检查行为，再检查工程质量；复用仍有效的验证证据 | `dev-review` |
| 需要证明实际用户路径可用 | 驱动真实应用，核对结果与副作用，维护可重复验证方法 | `dev-verify` |
| 目标是改善延迟、吞吐、资源或其他测量指标 | 固定工作负载和口径，完成取证、优化或公平比较，复用同一份基线 | `dev-benchmark` |
| 要创建 PR、跟进 CI/审查或合并已验证改动 | 选择 PR 交付分支，完成目标范围内的提交、跟进或落地；只要求 PR 时不执行环境部署 | `dev-deploy` |
| 要向指定环境发布 | 选择环境部署分支，确认环境与版本，执行授权部署，验证实际服务并记录 | `dev-deploy` |
| 需要清晰的文档、提交说明或 PR 简报 | 按读者问题组织信息，给出具体行为、证据与必要取舍 | `dev-writing` |
| 一个需求已经交付或明确停止 | 整理新知识、修复冲突、保留有价值的理由并归档过程 | `dev-archive` |

已有规格沿用，不重做访谈；涉及新的可见布局、交互或用户明确要求可视化对齐时，还要核对 `dev-prototype` 的实际产物、版本与用户确认范围。已有同内容同范围的有效确认直接复用；缺少确认只限制依赖该体验决定的实施，其他已授权工作继续。纯文案小修、无新可见交互的内部重构不强制虚构 UI；明确要求展示 API/CLI/后台行为时用 HTML 模拟说明并标清边界。只要求设计就交付设计；只要求解释就停在解释。读 [推进与恢复](references/execution.md) 处理并行和中断。需要完善需求时读[需求到实施的阶段衔接](references/workflow-routing.md)，执行已选任务时读[工程执行方法](references/operating-method.md)；它们补充当前阶段，不重新选择已完成的阶段。

复杂任务没有合适现成流程时，用[定制执行方法](references/custom-workflow.md)形成可验证单元并继续已授权工作。长任务的记录与事后复核使用[决策证据方法](references/decision-trail.md)，检查决定、替代方案与实际证据是否对应；只要求复核时交付审计结果，不自动继续迁移或实施。追查某项设计当时为何被采用由 `dev-why` 负责。用户明确要构建可操作的状态面板时，将它作为实施任务；仅查询进展使用 `dev-status`。

## 让工作能继续

本套技能新增的项目资料统一以 `.agents/dev/` 为根，按需使用以下分区。已有资料按真实位置查阅并保留必要引用；只有明确要求迁移时才搬迁，并保留内容、标识和有效链接。用户本次明确指定其他位置时按其指令执行：

- `.agents/dev/changes/<日期-主题>/`：按需保存当前需求、计划、进展与证据。brief 或 spec 选择一处作为权威行为契约，其他资料引用它；确认原型保留在 `prototype/index.html` 及本地资源，确认与走查记在 `prototype-review.md` 或已有等价记录。
- `.agents/dev/notes/`：经过验证的术语、背景、决策、错误经验和模块理解；入口 `index.md` 只指路。
- `.agents/dev/deploy/<环境>/`：部署手册及 `releases/` 下的历史发布记录。
- `.agents/dev/archive/changes/implemented/`、`rejected/`：由 `dev-archive` 在归档时按结果分流，并将目录重命名为 `<type>_<YYYY-MM-DD>-<slug>/`，保留创建日期；旧历史不自动迁移。退役知识仍放 `.agents/dev/archive/notes/`。

安装器选中任意 dev 技能时补齐 `.agents/dev/AGENTS.md`、开发六类目录和两个归档结果目录的九份短导航；选中 system 技能时另补系统根说明。固定位置的模板说明自动更新，根指令与业务记录不覆盖，不生成空业务记录，技能不重复维护初始化方法。按任务显式读取开发根与相关目录说明，不假定宿主自动递归加载。活跃 change 保持原命名，各阶段沿用同一真实路径，分类只发生在收尾。

这些是目标项目的资料，不能写进安装包 `.agents/skills/`。需要保存上下文、交接、接续或明确暂停时调用 `dev-handoff`，沿用同一变更目录和已有规格、计划与证据；具体方法和模板由它维护。接续后继续当前执行阶段，只有阶段尚不明确时才由本技能协调。

## 收束

对照最初交付目标，给出实际改动、当前版本的验证证据、交付地址或提交，以及确实未完成的部分。需要上线但尚未部署，明确写“实现已完成，部署未完成”；部署成功后，把可复用知识与最新代码引用整理进项目，而非把聊天记录全量塞入 AGENTS.md。


## 完整本地资料

按 [资料索引](references/method-index.md) 选择本技能负责的完整流程、示例和模板。本包维护本职责的方法，其他阶段调用对应技能；只读取当前任务分支需要的内容。
