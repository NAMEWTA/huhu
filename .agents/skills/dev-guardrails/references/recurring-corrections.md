# 把重复纠正转成可靠约束

用户纠正、同类错误重现或现有规则仍被跳过时，先找出为什么局部看似正确的改动会破坏整体，再评估成本相称的结构修正。只有足够证据和实际保护价值才引入机制。当前问题仍在用户授权内处理；发现范围外的结构问题时，留下候选和证据。

智能体可能只读取少数文件、复制近处示例、选择能编译的最短路径。用这个风险模型检查仓库，让常见正确路径清楚，错误路径尽量难以产生；不要据此假定每位贡献者都缺少判断。

## 找出错误类别

读取任务相关的近期提交、回滚、PR 审查评论、项目指令、绕路注释和当前范围内的纠正记录，按根因和触发机制分型。用真实独立事件判断重复；同一事故的多份报告只算一次。发生两次是可用识别信号；单次高风险且可复现的问题可以直接治理。查找范围限于相关模块和已授权证据。

每类写明症状、触发条件、证据与影响，区分规则缺失、规则不可见、机制无法执行，以及原规则本身错误。确认最新用户目标，不能用历史约束否定新需求。

## 在最高有效层处理

1. **架构消除。** 每份状态有明确所有者，常见任务有清楚的受支持路径。隐藏内部，阻止错误导入；用单一事实来源代替手工同步列表；移除会被复制的死代码与旧路。外部兼容或多种真实使用方式仍有必要时，不强行压成一条路径。
2. **类型表达。** 能让错误状态无法表达时，用类型限定可构建的值和调用边界。
3. **机械检查。** 无法由类型表达且规则稳定时，复用现有 lint、CI 或运行时检查。让错误信息指出正确文件、类型或函数，核对误报与维护成本。历史债务普遍存在时可以先限制新增实例，写明覆盖范围、退出条件与后续责任。
4. **行为验证。** 按[行为验证](behavior-tests.md)检查测试是否会在真实行为损坏时失败、仅内部重组时仍通过。修正弱断言和自证测试；保留仍保护契约的检查。
5. **判断性说明。** 为不能可靠编码的取舍保留简短理由、失败例子与源码入口，保存必要业务背景。

## 修复并证明

按频率、影响和本次范围选择最值得处理的类别，不自动全库重构。每类形成可审查的小变更，提交按已有授权与项目流程进行。

新增检查应能捕获真实历史错误或代表同类机制的最小复现，同时通过合法场景。用隔离片段或工作区检验，不污染生产数据或共享分支。本地与 CI 尽量使用同一命令；平台不同就说明等价条件。没有运行条件时标明尚未证明，不伪称规则已有效。

例外或抑制放在最接近的受影响位置，说明理由和重新核对条件；确有时效时写到期时间。按项目现有约定处理已有审批与权限。

## 维护最小规则索引

规则较多且需要导航时，在 `.agents/dev/notes/context/` 记录“规则 → 执行机制 → 证据”，按真实位置引用已有指南或模块文档。根 `AGENTS.md` 只保留高频约束和入口，不强制把整张表塞进去。已有规则反复被违反时，先判断机制为何失效，再按有效层处理。

复验通过后检查旧指令是否还有独立作用。结构已完全覆盖错误路径时，删除重复操作指令，保留仍有价值的理由、兼容边界和例外。记录观察到的错误、实际机制、失败与通过证据及旧指令处置，只更新亲自核对的范围。

## 交付

逐类说明证据、选用层级、更高层为何不适合、实际修正、检查辨别力及未覆盖范围。没有值得新增机制时，说明局部修复为何已经足够，不制造规则数量。
