# 回忆工作上下文

**开始或恢复工作之前，重建用户最近的工作上下文，返回紧凑的现状概括和下一步。**

保持紧凑、切题。只读取范围内工作线索所需要的内容，然后停止。

上下文存在两份记录中。自己的聊天历史保存你做过什么、决定过什么；共享记录保存在其他名字之下围绕相同代码发生的一切：用户反复报告的症状、已经上线又被回退的修复，以及生产中仍在发生的错误。第二份记录是 `dev-why`（决策调查）跨源码管理、工单系统、聊天与问题频道、长文档和错误跟踪系统搜索的内容。长期伴随缺陷的功能，其故事多数留在那里，因此不要只从自己的会话记录重建它。

用 `dev-session-history` 定位并核验原生记录。没有日志、权限或该技能时，使用当前对话、宿主已提供材料、已有交接与项目记录，并注明证据范围。

1. 确定输出。回忆是在行动前跨近期会话加载工作上下文。具体旧会话接续交给 `dev-handoff`，将稳定工作习惯整理成技能交给 `dev-personalize`。按用户要求直接撰写工作总结时，沿用已知事实和目标读者。如果用户已给出完整状态胶囊，包括路径、分支和改动，就使用它并跳过挖掘。
2. 搜索前固定范围。明确时间窗口：“最近”必须是真实区间，默认最近 7 天；明确用户指出的主题，以及工作区，默认当前活动工作区。未被要求时，绝不读取另一个项目的会话记录。复述搜索范围。绝不悄悄把“全部”改成“最近 N 条”。
3. 先筛选会话，再读相关片段。候选按实际修改时间排序，按会话中的事件确认时间范围；先检索主题，跳过当前会话和明显无关的子代理、评估及测试会话。每条会话提取主题、用户目标、决定、未完成线索、困难与纠正、产物（PR、工单、分支），每项引用会话 ID 和必要事件指针。一两条会话直接查；独立材料较多时，按任务成本、现有授权、实际工具与主机预算分工，复用仍有效的环境记录和 worker。每个读取者只接收授权范围内的材料，主线程只收简短发现，不流转原始记录。无法并行时顺序完成。
4. 主题涉及功能、文件、子系统、区域或缺陷时，查相关共享记录，“我在 X 上的工作”也属于这一类。复用 `dev-why` 的逐来源方法，询问“目前状态怎样、试过什么却没能持续奏效、用户还在报告什么”。独立来源的查询可以与会话检索同时进行。区分「检索无结果」和「来源不可用或未检索」，再将结果合入简报。不带具体对象的纯活动回顾，例如“我这周做了什么”，仅用会话及实时状态即可。
5. 对照实时状态验证。用 `git`、`gh` 或实际可用证据核对检索找到的 PR、分支、工单及有关运行事实。如果答案取决于代理实际做了什么，例如运行了什么工具、读了什么文件、遇到什么错误，就沿原会话读取相关完整事件轨迹。旧对话与当前事实冲突时，在简报里指出差异及各自的依据。
6. 按下面的输出契约撰写简报。按工作线索分组，始终围绕指定主题。

## 输出契约

先给状态胶囊，再给各条工作线索的状态，然后列问题，最后给下一步。更深细节放后面或删去。

- **状态胶囊。** 最多 5 个要点。说明这项工作是什么、整体到哪里了。
- **工作线索。** 每条一行，用一个清楚的实际状态说明，例如：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。状态是简洁的说明，不建立必须驱动流程的状态机。
- **问题。** 最多 5 项，选择反复出现的。包括用户反复报告的症状，以及已上线又回退的修复，让下一次尝试从上一次失败的位置开始。
- **下一步。** 一项最有用、具体的后续动作。

相邻功能或工单除非阻塞当前目标，否则不纳入。当状态胶囊和工作线索超过一屏时，先删细节，不先删工作线索。通过`dev-writing`（清晰写作）撰写简报；聊天发现用 UUID 引用，共享记录发现引用其来源，例如 PR 编号、工单 ID、聊天永久链接、错误跟踪问题；公开输出前脱敏私人上下文。

默认直接返回简报。用户要求保存，或当前 Change 确实需要这些材料接续时，在已有上下文、进展或交接记录中放一处必要的脱敏引用。简报的下一步是一项建议，继续执行沿用当前任务的授权。
